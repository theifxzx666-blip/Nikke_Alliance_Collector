> **为什么主程序叫 `alliance_ocr.py` 而不是中文名？**
> Windows 的 `.bat` 用 ANSI(GBK) 解码，文件里只要出现 UTF-8 中文就会整段乱码、脚本直接失效。
> 所以 bat 脚本严格保持纯 ASCII，主程序也用 ASCII 名，避免路径中文被误读。

## 界面：为什么是竖版

竖版不是审美选择。这个工具要**贴在游戏窗口旁边常驻**，横版会横向抢位置；而且竖着
只有一条视线，出问题时"卡在第几步"一眼就能看出来，不用左右扫。

形制参考 ArcanaHelper V1.1.2（616×839 的竖窗），本工具是 620×940，从上到下就是
一次采集的真实顺序：

```
标题
目标窗口条        接的是谁 · 画面多大 · 区域标没标
①②③④⑤ 步骤条     接窗口 → 进成员页 → 校人数 → 滚采 → 入库
本屏预览          红框标出候选行
进度条 + 任务提示   「滚采中 · 第 24 次滚动 · 页面共 32 人 · 已采 28」
成员名单          双击可删误识别
台账              待采 / 已识别 / 已跳过
运行日志          常驻 5 行、采集时 9 行，实时停在最新一条，可拖高可折叠
[开始][暂停][继续][取消]
进成员页 / 采集本屏 / 标定昵称列 / 格每次
导出CSV / 昵称库 / 成员变动 / 打包日志 / 同步 / 测试滚动 / 手动框选 / 清空
```

**步骤条只有四种状态**：灰=没轮到、蓝=正在做、绿=做完了打勾、红=这步失败。
"入库"这一步是判断题——完整采集点绿，残缺一律点红。颜色比文案先被看到，
这是刻意的。

**四键语义**（和原来"一个键翻来覆去变身"不同）：开始后`开始`置灰，`暂停`可点；
暂停后`继续`可点；`取消`随时可点，但取消的一轮**不算完整采集**，昵称库不记帐。
暂停不会打断正在飞的那一屏，只在下一个动作前停——半路撒手会留下半屏截断。

**校人数**是新增的一步，也是唯一能自证"没漏人"的硬证据：进成员页时读一次页面上
的 `(n/m)`，收工时拿它和名单对账：

| 情况 | 结论 |
|---|---|
| 页面上 32，采到 32 | ✅ 一致，这轮可以记帐 |
| 页面上 32，采到 34 | **裁到 32**，去掉只露一屏的误读，并点名是哪几个 |
| 页面上 32，采到 30 | ⚠ 中间漏采了，这轮不算完整 |

滚采期间所有判据（重合行、行距、死区）只能证明"没跳步"，证明不了"起点在第一行"。
**工具自己说了不算，页面上那个 n/m 才算。**

## 运行日志：跟到最新，也翻得回去

采集时最常冒出来的一句话是"我想看一眼日志"。所以这块不是装饰，它有三条硬要求：

| 要求 | 做法 |
|---|---|
| 新行一进来就在最下面 | 每批写完 `see("end")`；末行加淡底，眼睛能直接落在最新那条 |
| 别只有 5 行高 | 开跑自动撑到 9 行，收工让回给名单；右侧 `⇕` 可上下拖，拖过就固化 |
| 翻历史时别被拽回来 | 用滚轮往上一滚就停止跟随，标题变蓝 + 右下角 `↓ N 条新`；点它或滚回底部自动恢复 |

**为什么写入要过队列而不是直接写。** 日志是从采集线程写的。在子线程里直接碰 Tk
会偶发抛 `main thread is not in main loop`，而 `log()` 外层有 `except` 兜底——错误
被吞掉，行也**静默消失**，偏偏缺的常是最关键那条。所以外部只用 `push()`，它只往
队列塞；主线程每 80ms 抽一次，批量入库后统一滚动。

**一个 Tk 的坑记在这里**：`Text` 在 `state="disabled"` 下，连程序化的 `delete` 都会
被**静默忽略**（不报错、也不删）。裁剪和打标必须在恢复只读之前做完，否则日志会一路
涨过 400 行还不止。实测踩过一次，400 行上限形同虚设。

日志文件才是全量（`输出/操作日志.txt`，超大自动轮转），界面只留最近 400 行。

## 采多了要裁，不能只告警

页面上那个 `(32/32)` 是**唯一不依赖识别质量的硬事实**。所以人数超了必须在进库
**之前**裁到一致——只告警是不够的：实测「腊目夜」「入魔工」各在库里活了两轮才被
移出，期间每一轮都在教昵称库"这两个是成员"。

裁的依据只有一条：**真成员每屏都在，误读只闪一两次。** 整趟 24 屏里平均每人出现
3~4 屏，而误读全是 1 屏——这个差距比字面相似度可靠得多。之所以不再指望"字面像不像"，
是因为实测漏网的这两个，成因完全不同：

| 多出来的 | 真名 | 怎么躲过位置合并的 |
|---|---|---|
| 腊目夜 | 朧月夜 | 相似度 0.667 够、位置也对，但它落在那一屏的**最后一行**，下一屏已经滚出去，位置证据没有第二次机会 |
| 入魔工 | 大魔王 | 四个字读成三个完全不同的字，相似度只有 **0.33**，比 `same_row` 的 0.5 门槛还低 |

三道保护，少一道就会把真人当误读删掉：

| 保护 | 阈值 | 防什么 |
|---|---|---|
| 只从"屏数 ≤ 1"里挑 | — | 真成员至少出现 2 屏，这是下限不是统计猜测 |
| 单轮最多裁 5 个 | `MAX_TRIM` | 超出说明是别的问题（例如总数本身读歪了），靠丢名字掩盖更糟 |
| 页面人数要在 3~200 | `TRIM_TOTAL_RANGE` | 那个数字也是 OCR 读出来的，一样会歪成 `1` 或 `999` |

可裁的不够时**宁缺毋滥**：只裁能裁的，剩下的原样留着并明确告警"请人工核"——绝不
拿屏数 2 的真成员凑数。

## 开跑前先确认页面

点【开始】之后、真正拖动之前，会先用场景识别确认"确实在联盟成员页"，连续 2 次
一致才开跑（对应 ArcanaHelper 的 `连续=2/2`）。判定按 ArcanaHelper 的
`Recognizer.classify` 的打分方式写，日志长这样：

```
scene: 页面判定 1/2 · 最终选择=联盟成员页 · 连续=1/2。
       联盟成员页:命中率=1.0000/1,误差=0.0000,成功=True,原因=指纹命中率通过；
       联盟概览:命中率=0.1667/3,误差=0.8333,成功=False,原因=指纹命中率不足；
       主页:命中率=0.0000/3,误差=1.0000,成功=False,原因=指纹命中率不足
```

为什么不只报"成功/失败"：只给一个 False，谁也说不清是差一个词还是整页都不对。

**认不出页面时不拦**（`认不出 ≠ 不在成员页`）。只有明确认出"在别的页"才停手，
并把步骤条第 2 步点红。也不弹模态框——面板就在眼前，弹窗只会挡住用户去点
【进成员页】，还给脚本化测试添一个死锁点。

## 同步接口（预留）

默认 `enabled=false`：**只留档，不联网**，一行网络请求都不会发。

一次采集结束就往 `输出/<运行目录>/sync/outbox/` 写一条 json，先落盘再考虑发。
配置在 `预设/同步.json`：

```json
{
  "enabled": false,
  "base_url": "https://api.example.com",
  "api_key": "",
  "timeout": 8,
  "endpoints": { "members": "/third/bot/nikke/v1/syncAllianceMembers" }
}
```

| 行为 | 说明 |
|---|---|
| 落盘 | 一条记录一个 json，天然幂等；发失败留在原地，下次启动重投 |
| 端点 | 别名 `members` 或完整路径/URL 都行，改配置不改代码 |
| 鉴权 | `Authorization: Bearer <key>`（头名和前缀都可配） |
| 失败 | 留诊断 `{status, error_type, reason, endpoint, method, attempts}`，只说"同步失败"等于没说 |
| 补投 | `flush()` 每次最多重投 20 条，成功的移进 `outbox_done/` |

载荷结构现在按"后端最可能要什么"定的（人数/总数/是否完整/每人名字+置信度/采集时间），
字段名一改就在 `sync_payload()` 里改一处。

## 怎么用

### 三步，然后开跑

工具只服务**胜利女神：新的希望**的 PC 客户端，所以连"接哪个窗口"这件事都不用你操心：

1. **打开客户端，工具自己接上**（后台每 2 秒扫一次，标题/进程名命中 + 有效画面 16:9）。
   界面上没有「锁定窗口」这个按钮——连续 10 秒接不上，信息条右侧才会冒出「手动选择窗口」兜底。
   信息条会写清比例：`已连接：… ｜ 窗口 736×444 · 画面 720×405（16:9 ✓）`
2. **进成员页** —— 在主页点一下就行：它自己点右侧「联盟」→ 落到联盟页 → 点顶部「队员」→
   进到成员列表，再把列表拉回第一行。**每一步点之前都先确认自己确实在那一页**，
   判不准就停下来告诉你停在哪，绝不盲点（详见下面「导航」一节）
3. **自动滚采** —— 已经站在列表第一行就直接点它，自己滚、自己认、自己停

首次用需要**标定昵称列**（一般不用做，内置预设已覆盖 16:9 的各种分辨率）；
需要重标时点【标定昵称列】，浮层先自己认，认出来点【提交】；认不出就拖个框再提交。

采完点 **导出 CSV**。

> **第 2 步基本不会用第二次。** 标定结果会固化成 `预设/昵称列预设.json`，里面存的是
> 「占有效画面的比例」和「行距占画面高度的比例」，所以换分辨率、换机器、删掉 `输出/`
> 目录、甚至重装，只要这个文件在，工具自己就知道昵称列在哪。
> 唯一需要再标定的情况：游戏改版 UI 把列表布局改了。

采集期间游戏窗口会被顶到前台（否则输入发不进去），本窗口退到后面，**这是正常的**；结束后窗口会自动跳回来。

12 人实测 11 秒，32 人大约 25~30 秒。

## 导航：从主页一键走到成员页

点【进成员页】，路径是死的两步：

```
主页 ──点右侧「联盟」──▶ 联盟概览 ──点顶部「队员」──▶ 成员列表 ──滚轮拉回第一行
```

**为什么不用像素模板找按钮**：改版改一个图标就能让整套模板报废，而按钮上的
「联盟」「队员」这几个字几乎不会变。代价是一次全屏 OCR（0.3~0.8 秒），放在两步
导航里完全够用。

### 三条铁律

| 铁律 | 做法 | 失效时 |
|---|---|---|
| **先证身在何处** | 每页配一组"该页独有"的词（主页 6 个、联盟页 6 个），命中够数才认 | 判不准就停，绝不"猜最近的那个页面" |
| **只许点白名单** | 每步只框住一个小矩形（右侧竖排 / 顶部标签条） | 落点算到框外一律拒绝，宁可不动 |
| **点完必须验页面变了** | 等目标页指纹出现，最多等 1.5 秒 | 没变就报"可能被弹窗挡住"并收手，**不重复点** |

第三条是重点。在没认出来的页面上重复点击，是唯一可能造成实际损失的动作。
工具宁可停在「联盟概览」这一步报错，也不会为了"试一下"多点和游戏相关的按钮。

### 白名单里永远没有的东西

抽卡、商店、付费、钻石、设定、退出——这些按钮的实测坐标全部落在白名单外，
`navtest.py` 第 3 组就是拿真实截图逐个断言这件事。所以即使哪天坐标换算错了，
点到的也只是画面空白，不会点进付费项。

### 认不出字的时候怎么办

退到**实测锚点**（用户 1236×725 截图上红框中心换算出的比例坐标），但有两个前提：
页指纹已经通过、锚点本身也在白名单内。日志会写清是哪种方式点的：

```
[nav] 点「联盟」@(1190,290) · OCR 认出「联盟」@(0.969,0.418) 置信 1.00
[nav] 点「队员」@(614,193) · OCR 没认出「队员」，退回实测锚点 (0.500,0.278)
```

### 到位之后会把列表拉回第一行

上一轮采集总是停在列表底部。如果下一轮就地从中间开始，前面那截人**永远采不到**，
而且日志上完全看不出来，只表现为"这次比上次少了十几个人"。所以导航收尾会用滚轮
向上滚，直到画面不再变化。

滚轮到底管不管用，用你这台机器以前采过的记录判断（`scroll_mode` 存的是 `wheel`
就直接信它；没有记录就保守报"未确认"，让你手动拉一下）——**不会假装成功了**。

### 坐标采集器：`clickprobe.py`

导航锚点全是"从截图反算出来的比例坐标"，算错了、或者哪个按钮突然长歪了，
光看日志只能知道"点了但页面没变"，不知道差在哪儿。这个独立小工具专门补这一段：

```bash
.venv\Scripts\python clickprobe.py
```

打开后照平常点游戏（先在主页点右侧「联盟」，进联盟页后点顶部「队员」），
它只记**游戏在前台时**的点击，每次存三样东西：

| 记什么 | 怎么来的 |
|---|---|
| 屏幕坐标 → 画面比例 | 点击瞬间重算一次有效画面，不缓存 |
| **点前**画面 | 环形缓冲（每 0.12 秒一帧、留 3 帧、取最老的那张），保证一定早于点击 |
| 点后画面 + 全屏识图 | 等 0.9 秒再截，跑一遍 det+rec，再把「离你点的位置最近的字」排出来 |

点【生成报告】就会告诉你：

```
#1  屏幕 (1336,375)  画面比例 (0.973,0.423)
    点前→点后差 41.2（画面变了）
    识图 33 块，离点击点最近的：
      「联盟」  中心 (0.973,0.423)  置信 1.00  距点击 0.001
```

**偏差一栏是关键**——0.001 说明点正了；0.4 说明点的是别的东西。
报告存 `输出/坐标采集_<时间>/`，同目录还有每一次的点前/点后原图，可以直接看图核对。

窗口可以收起成一条 36px 的状态条，不挡游戏。另外它**不用启动主程序**，
单独跑也不加载昵称列那套东西。


## 锁定窗口锁的是什么

锁的是**有效画面尺寸 + 宽高比**。有效画面 = 客户区去掉游戏自己加的黑边，
也就是真正渲染 16:9 的那块矩形。采集区按「占有效画面的百分比」保存，不是屏幕绝对坐标。

| 你做的操作 | 结果 |
|---|---|
| 把游戏窗口拖到别的位置 | 自动跟随，不用重标定 |
| 改窗口大小但画面仍是 16:9 | 自动按比例缩放，不用重标定 |
| 把窗口拉成 16:10 / 放上 21:9 显示器 | 程序自己找画面、自己裁黑边，照样不用重标定 |
| 有效画面本身不是 16:9（游戏被拉伸） | **拒绝采集/标定**，要求把窗口调成 16:9 |
| 最小化游戏 | **拒绝采集**，提示还原窗口 |
| 采集区被别的窗口盖住 | **拒绝采集**，并点名是谁挡的 |
| 游戏重启（窗口句柄变了） | 需要重新锁定（句柄不跨进程保持） |

为什么基准是有效画面而不是客户区：窗口比例不是 16:9 时，游戏会把 16:9 画面居中显示、
两侧或上下留纯黑。这时拿「客户区百分比」算坐标会整体偏移——画面变窄 1%，
昵称列的实际位置就偏 1% × 客户区宽。基准换成有效画面之后，黑边被程序自己裁掉，
**你不需要手动把窗口调成 16:9**。

为什么有效画面不是 16:9 时要拒绝：NIKKE 的 UI 锚点跟着画面比例走，比例变了 UI 会重排，
此时百分比坐标算出来就是错的。自动改窗口尺寸比让你自己拖一下危险得多，所以只提示、不动手。

这也是原来最危险的隐患：旧版存屏幕绝对坐标，窗口一挪程序自己察觉不到，截到错位置时如果碰巧有文字，就会**静默采进错误名字**。现在这种情况会被前置校验拦下。

## 六道保护

| 情况 | 表现 |
|---|---|
| 这条列表不吃滚轮 | **自动换方式**（拖动 → 滚轮 → 翻页键），哪个真让名字变了就用哪个，并记进配置 |
| 到底了 | 连续 3 次没有新人 → 自动停 |
| 一步跨了一整屏 | 两屏没有重合名字 → **立刻停**，并把步长压到很小（下次一步只走一两行） |
| 确实跨过了中间的人 | 本屏行数比上一屏少且全不重合 → **立刻停**，明确告知漏了人 |
| 一步只走一两行（正常） | 继续，且每轮按实测校正步长 |
| 游戏被切走 / 被遮挡 / 比例变了 / 最小化 | 每轮截图前校验，任一不满足就停并说明原因 |
| 游戏不在前台 | 每轮比对前台窗口，掉焦点先抢一次，抢不回来才停 |

判断"到底有没有滚动"用的是**名字序列**，不是画面差。这一点很关键：联盟成员列表不吃滚轮时，鼠标悬停高亮仍会让画面差变成 1.3，旧版据此判定"滚动了"，于是连采 3 轮无新人、误报成"已到底"。现在只有"上一屏的名字在本屏以相同顺序出现"才算滚动，日志里直接给出实际行数：

```
16:42:23.910 [I] auto: 本屏 5 行 · 与上屏重合 3 行 → 这次走了 2 行（拖动）
```

**漏人怎么判**：只有"这次滚过的行数 > 本屏行数"，两屏之间才会留下谁都没拍到的行。恰好换了一整屏（上一屏名字全消失、本屏全新）是紧挨着的，**不算漏**——32 人每屏 5 行时，正常采集几乎每一步都是这个形状。旧版拿"上一屏末尾两行消失"当判据，把正常采集一路误报成滚过头（实际那次采到 14 人时停下的原因就是它，名单 1..14 连续，一个没漏）。

名字序列有个绕不过去的天花板：两屏完全没有重合行时，位移量只能量到"至少一屏"，"刚好一屏"和"跳过几行"在数据上长得一模一样。所以不能既不停又不误报——正确做法是让这种情况根本不发生：**步长闭环收敛到每次 2 行**，每屏 5 行时永远留着 3 行重合。

## 列表滚不动怎么办

联盟成员列表实测**不吃滚轮**：1 格和 5 格都试过，画面差只有 1.3（鼠标悬停的高亮动画），名字一个没变。

所以工具不再假设"滚轮就能滚"，改成三种方式依次试，用**名字有没有变**来判定，而不是猜：

| 方式 | 做法 | 适用 |
|---|---|---|
| 拖动 | 在采集区按住往上拖一小段（距离由工具自己算） | 手游式 UI，联盟成员列表就是这种 |
| 滚轮 | 滚 1~20 格 | 常规 PC 列表 |
| 翻页键 | PageDown | 列表支持键盘 |

**拖动带惯性，所以距离不能写死。** 实测同一段 160px 的拖动，一次滑出 284px、一次滑出 355px（1.8~2.2 倍），滑多少不稳定。滑满一屏就完了——两屏没重合行，中间漏没漏人谁都看不出来。所以工具用闭环：

```
拖动距离 = 目标行数 × 实测行距 ÷ 实测惯性倍率
```

行距从每屏识别到的昵称 y 坐标取中位差，惯性倍率从"上一次拖了多远、实际走了几行"反推。实测两步就收敛：

```
第 1 次 · 拖动 拖 70px（行距 ?px · 惯性 2.00）→ 走了 2 行
        滚了 2 行 → 实测行距 60px · 惯性 1.70（均值 1.85）· 下次拖 64px
第 2 次 · 拖动 拖 64px（行距 59.5px · 惯性 1.85）→ 走了 2 行
第 3 次 · 拖动 拖 65px（行距 60.5px · 惯性 1.87）→ 走了 2 行
```

右下角 **「测试滚动」** 一次跑完三种，直接告诉你哪种有效、一次走几行：

```
状态栏：这个列表要用【拖动】才能滚：一次 1 格 ≈ 3 行（本屏 5 行，重合 2）
```

结果写进 `输出/区域.json` 的 `scroll_mode`，之后自动滚采直接用它。就算你没测过，自动滚采发现"名字一个没动"也会自己换下一种，**不会把"滚不动"误报成"已到底"**——旧版就是栽在这。

权限方面有条和直觉相反的实测结论：

| 组合 | 输入能注入吗 |
|---|---|
| 游戏管理员 + 工具普通权限（`nikke.exe` 的常见情况） | **能** |
| 两者都是普通权限 / 都是管理员 | 能 |

UIPI 拦的是窗口消息（`SendMessage`/`PostMessage`）和钩子；`mouse_event` 走系统输入队列，不受限制。所以**不需要**给工具加管理员权限。

真正会静默失败的是抢前台：`SetForegroundWindow` 被前台锁拒绝时不报错也不返回错误。现在改成三级兜底（直接切 → `AttachThreadInput` → 模拟 Alt 键释放）并检查返回值，切不过去当场提示。

`格/次` 这个数字：滚轮模式下就是滚轮格数；拖动模式下是**目标行数的倍数**（1 格 = 2 行，2 格 = 4 行）。一般不用动它——工具会自己按实测校准到每次 2 行。只有在列表很长、想快一点时才调大，代价是留出的重合行变少，跨屏告警更容易触发。

## 拖动这一步是怎么定下来的

「一步走一行」这句话听着简单，但它由三个数决定，每一个都是实测量出来的，猜错任何一个都会出现"突然猛地下滑到底部"或者"每次只采到一半"。

### 一、起手死区：拖 70px 只挪 57px

游戏在手势起手的前十几像素里只做一件事：区分你这是点击还是拖动。这段位移**不产生滚动**。实测（`拖动标定.py`）：

| 拖动距离 | 内容实际位移 | 差出来的死区 |
|---|---|---|
| 60px | 42px | 18px |
| 70px | 57px | 13px |
| 89px | 71px | 18px（正好一个行距） |

所以"拖多少像素就走多少像素"是错的。按行距 71px 给步长，真实位移只有 **0.80 行**——每一步都差一点，相位一路往后漂；漂到某一步正好跨不过行边界，名字就一个字不变。而旧逻辑把"名字不变"直接当成"列表到底了"，于是 32 人的联盟**只采到 6 个人**就报"✅ 已到列表末尾"。

现在步长 = 行距 × 1.25 + 死区 ≈ 104px，真实位移稳定在 1.15~1.35 行。另外"走 0 行"不再直接判定到底，先**把步长放大一倍再试一次**：真到底了放大也推不动，卡在两行中间的话一步就跨过去了。

### 二、拖动速度：250px/s 会甩屏，107px/s 不会

同一个距离，速度不同结果完全不同。首步 3px、间隔 12ms（≈250px/s）时，实测每 5~10 步就会甩一次，松手后惯性把列表滑掉整整一屏（两屏零重合，中间的人全丢）。降到 3px / 28ms（≈107px/s）后连续 28 步零跳步，位移稳定在 87~91px。

| 速度 | 连续 14~28 步内的跳步次数 |
|---|---|
| 250px/s（每步 3px / 12ms） | 每次跑都会出现 |
| 120px/s（每步 3px / 25ms） | 0 |
| 67px/s（每步 2px / 30ms） | 0 |

慢的代价是每拖一次多花半秒，换的是"一步就是一步"。

### 三、松手之后不许马上动光标 ← 「突然下滑到底部」的真凶

这一条是最后找出来的，也是最隐蔽的。拖完松手之后，程序要**立刻**把光标从拖动终点请出去（不请走的话，卡片悬停高亮会让"等停稳"永远等不到）。问题在于这个动作是**瞬移**：从拖动终点 `(604,631)` 直接跳到画面角落 `(63,184)`，横向 540px。

游戏处理 `LEFTUP` 要晚一两帧。这一两帧里它仍然认为手指按着，于是这 540px 就被当成一次**大甩动**，列表一路甩到最底部。

证据是跳步的落点：不管从第 4 行、第 5 行还是第 12 行开始跳，**落点永远一模一样**，而且正好是名单的最后 5 行（也就是列表底部）。只有一个绝对位置才会这样——不是距离算错。

修法是在 `LEFTUP` 之后先停 180ms（`RELEASE_SETTLE`），谁来都不许动光标。改完连跑四轮，每轮都是 24 次滚动、32 人、零跳步。

> 诊断这一条用的工具是 `速度实验.py`（同一距离换速度连拖，统计跳步次数）和 `逐帧.py`（把每一步 `scan` 的原始输出和 ROI 原图都存下来）。这一轮两次都被自相矛盾的数据带偏过：一次是 `judge_roll` 的两个参数写反了，报出"走了 5 行、零重合"；一次是只看名字推断位移，把"1.0 行"和"1.35 行"当成一回事。**像素位移和名字序列必须一起看**，两者打架就说明结论有问题。

## 滚完为什么要等一下

旧版发出滚动后就固定等 520ms 再截图。算一下就知道不够：拖动本身要 370ms（16 小步 × 12ms + 按下/松开延时），真正留给惯性的只剩 150ms，而实测松手后的惯性滑动要 200~400ms 才停。**结果是在列表还在滑的中途截了图**，截到两个位置叠加的中间态：行被拉花、名字串行，OCR 认出来的序列和上一屏对不上，于是被判成"漏人/跨屏"。

现在不用固定时长，改成**轮询到画面真的停稳**。阈值是按实测量级定的，不是拍的：

| 状态 | 相邻两帧的平均灰度差 |
|---|---|
| 真实游戏背景动效（Live2D / 粒子，永远在动） | 1.45 |
| 滑过一行 | 40 以上 |
| 判定阈值 | ≤ 5.0，且要连续两帧 |

松手后先等 300ms（惯性最大的一段），然后每 90ms 探一帧，连续两帧都没超过 5.0 就认为停住了，**通常 300~600ms 收工**。离背景动效（1.45）和滚动信号（40+）都差了近 30 倍，两边都够不着。兜底上限 2.2s——超时就按当前帧继续，并在日志里记一条警告，不会卡死。

> **为什么不用"画面总差不再变化"当判据**：试过，不行。总差会在"位移超过内容自身尺寸"之后**饱和**——测试里白条高 40px，位移 70px 和 90px 的总差都是同一个 102.00，于是惯性刚滑出半屏就被判成停稳，截到中间态。真实列表滚过一屏后画面同样完全不重叠、总差同样饱和。饱和是固有性质，不能拿来当"停止"的证据。

```
17:16:51.968 [I] roll:   第 4 次 · 拖动 拖 65px（行距 60.5px · 惯性 1.87）→ (1478,321)
17:16:52.587 [I] settle: 画面停稳 · 松手后 616ms · 总差 7.54
17:16:52.852 [I] auto:   滚了 2 行 → 实测行距 60px · 惯性 1.86 · 下次拖 65px（目标 2 行）
```

## 光标为什么要挪开

拖动结束时指针正停在拖动终点——列表中央的某张成员卡片上。指针停在名单上有两个后果，都不是"多等一会儿"能解决的：

1. 卡片**悬停高亮动画**让那块像素一直在变，"等画面停稳"永远等不到
2. 白色箭头**压在昵称字上**，被 OCR 当笔画认进去，一行名字断成两截

所以每滚一次就把光标挪到采集区外（优先客户区四角，采集区盖满四角时退到屏幕角落），挪完再开始等停稳；采完点停或到底，光标自动**还回你原来的位置**。

日志里会留痕：

```
17:16:51.966 [I] cursor: 光标在采集区内 (1478,369) → 挪到 (1218,141)
```

## 日志与诊断

出问题不用描述现象，**右下角「导出诊断包」**生成的 `输出/诊断包_时间.zip` 发过来就行。里面是：

| 文件 | 能看出什么 |
|---|---|
| `操作日志.txt` | 每一步做了什么、参数是多少、在哪一步停的 |
| `最近一屏.png` | 出问题时工具**实际截到的画面**（最有用——能立刻分清是框错了还是 OCR 认错了） |
| `环境.txt` | 窗口尺寸、区域相对坐标、权限对照、名单人数 |
| `区域.json` | 标定配置（相对有效画面的比例 + 行距 + 每屏行数），我能按同样的坐标复现 |
| `当前名单.csv` | 已经采到的人 |

诊断包里不含 `预设/昵称列预设.json`——它是"下次还能用"的东西，不该被反馈的问题数据覆盖。

日志本身是逐行动作记录，一次完整采集约 85 行 / 8KB：

```
16:09:52.068 [I] auto: 开始自动滚采 · 已有 0 人 · 滚轮 1 格/次 · window=600×420 · 1.429@1208,131
16:09:52.625 [I] capture: 采集 region=(1228, 211, 1728, 511) auto=True
16:09:52.740 [I] scan: 500x300 · 候选带 5 · 过色 5 · 识别 5 · 113ms · ['DORO', '曼殊颜华', ...]
16:09:52.773 [I] apply: auto=True 本屏 5 行 净增 5 累计 5 人
16:09:53.064 [I] roll: 第 1 次 · 1 格 → (1478,361) · 前台=True · 该点窗口=True
16:09:53.639 [I] ui: 滚轮 1 格 · 画面差 10.450 · 前台=True
```

级别：`[I]` 正常、`[W]` 告警（被校验拦下、连续无新人、跳行）、`[E]` 异常（带完整 traceback）。

**为什么这些字段值得记**：`scan` 那行的「候选带 / 过色 / 识别」能反推是哪一层出的错——候选带多但识别少是框进了头像，过色少是配色变了，识别有但名字怪是 OCR 认错。光看"识别结果不对"没法定位。

日志超过 2MB 自动轮转成 `操作日志.1.txt`，不会越跑越大。`[E]` 级别覆盖主线程、子线程、Tk 回调三条路径的未捕获异常——以前 pythonw 下这类崩溃就是"窗口凭空消失"，什么线索都不留。

## 启动不了怎么办

| 现象 | 处理 |
|---|---|
| 双击完全没反应 | 改用 **`调试启动.bat`**，控制台会直接显示错在哪 |
| 提示找不到 `.venv` | 先双击 `安装环境.bat` |
| 窗口一闪就消失 | 看 `输出/操作日志.txt` 末尾的 `Traceback` |
| 状态栏一直停在「正在加载识别模型…」 | 首次启动要加载 ONNX 模型，等 5~10 秒；超过 1 分钟说明模型文件缺失，跑 `安装环境.bat` |
| 锁定时列表是空的 | 游戏窗口被最小化了，还原后点「重新扫描」 |
| 采集时提示被「NIKKE 联盟名单采集」挡住 | 本工具窗口盖住了采集区，把它拖到旁边或缩小 |
| 自动滚采一开就停，说「切不到前台」 | 手动点一下游戏窗口让它真到最前，再点自动滚采 |
| 自动滚采滚不动、提示三种方式都试过 | 先点「测试滚动」看哪种有效；三种都无效说明列表只能拖滚动条，把诊断包发我 |
| 某一步「突然加速」滑到底，后面两屏对不上 | 已经修过：拖动到终点会先原地压住 0.2 秒再松手，把松手速度归零，惯性不再随机。仍出现就发诊断包，并注明这一步拖了多少像素 |
| 名单比游戏里少一两个人 | 先看日志里那一屏的「识别 N」和 CSV——缺的是不是「三/一/二」这类横笔多的名字。这类行曾被投影切成碎片整行丢掉，v3 已修（`bandtest.py` 盯着）。若缺的是别的字，把那一屏的诊断包发我，包里的 `最近一屏.png` 就是现场 |
| 名单比游戏里多出人 | 先看日志里有没有「同一行两种读法」「收工复核」这两类行。有就是已处理（同一行被读成两种拼写，按行位置并回一个，并按整趟采到过多少屏决定留哪个）。如果多出来的名字跟你实际成员完全不搭，把该屏诊断包发我 |
| 报错但不知道原文 | 看 `输出/操作日志.txt`，状态栏每句话都带时间戳记进去了 |

## 标定：框几次，提交就存

**结论：标定只做一次。** 点【标定昵称列】后浮层会先自己算一遍；算不出来就拖一个框，框几次都行，拖完点【提交】——**提交即存盘，不会有第二个确认窗。**

### 框是输入，不是答案

这是这一版最重要的原则：**程序不校验"你框得对不对"，也不因为自己认不出就拒绝存盘。** 以前的流程是"认不出 → 弹窗 → 关掉重来"，你列的那个框永远进不去；现在框进去就是采样，采样够了就提交。

| 你的操作 | 浮层顶部显示 | 结果 |
|---|---|---|
| 什么都不做（自动认出来了） | `自动认出 5 行 · 行距 70px` | 直接点【提交】 |
| 拖一个框 | `已采 1 次 · 中位数 386×275px · 5 行 · 行距 60px` | 觉得对了直接【提交】 |
| 再拖两次 | `已采 3 次 · 中位数 386×289px · 5 行 · 行距 60px` | 三个样本取中位数，更稳 |
| 拖歪了 | 提示条只换一句话，样本照收 | 继续拖，或直接提交 |
| 在行间空白点一下 | 照常给结果 | 不用重来 |
| 拖的框太小（<40×20） | 提示"框太小了" | 重新拖一次 |
| 画布上淡黄虚线 | 历史样本 | 绿色实线是中位数 |

### 为什么"框几次"在数学上真的更准

手拖同一个意图两次，落点差十到三十像素是正常的——这是人手的分辨率，不是错误。所以问题不是"怎么框准"，而是"怎么让噪声自己消掉"：

- **单次框** = 一个带噪声的样本
- **N 次框各分量取中位数** = 噪声按 √n 收敛

取中位数而不是平均值：手抖是双边的（有时框长、有时框短），平均值会被某一次拖飞了的样本拉偏，中位数不会。

```
5 次抖动的中位数 = 真实框（误差 0）
混进一个拖飞到隔壁栏的样本，中位数仍然不乱（误差 6px）
```

### 中位数之后再吸附一次行边界

中位数解决了"框在哪"，但框的上下边几乎不可能正好落在行间空白上——差十几像素就会切掉半行，而切掉的那一行 OCR 直接认不出，等于漏人。

所以提交前还会**借画面自己的结构对齐一次**：凡是**被框碰到**的行，都扩成完整的行。

| 你框成什么样 | 吸附后 |
|---|---|
| 比整列大很多（上下各多 30px） | 收紧到真实首末行 |
| 把首行、末行各切掉一半 | 两行都完整补回来，7 行仍是 7 行 |
| 框错到别的列（套在头像那一条上） | 原样返回，不瞎猜 |

关键细节：被切掉的行必须也能看到，所以是在**整幅画面**上找行、再挑"与框纵向有重叠"的那些。只在框内找行是不够的——框把某行切掉半截时，框内只看得见下半部分，对齐反而会把整行裁掉，越修越差。

x 方向不动：昵称长短差异大，自动收窄会切掉长名字；横向框宽一点只会多带进空白，识别链路本来就滤得掉。只修真正会看错的那一维。

### 存完立刻试拍一次

提交后工具会马上在那个区域拍一帧、真跑一遍识别，把结果写进状态栏：

```
已标定区域 101×316 · 每屏 5 行 · 行距 71px · 已固化为预设，以后不用再标定 · 试拍认出 5 行 · 点【采集本屏】
```

如果试拍认出 0~2 行，后面会跟一句提示（"框可能没套住昵称列"之类），但**不会撤销你的标定**——框是你给的，工具不该因为自己认不出就否定它。

### 结果会固化下来

提交后同时写两处：

| 文件 | 作用 |
|---|---|
| `输出/区域.json` | 本机最近一次标定，跟着窗口比例走 |
| `预设/昵称列预设.json` | **随工具走**的预设，换分辨率照样能用 |

预设里存的是比例而不是像素：

```json
"region_rel":   [0.4066, 0.3761, 0.4992, 0.8776],   // 占有效画面的比例
"pitch_rel":    0.1006,                              // 行距 ÷ 画面高度
"rows_per_screen": 5,
"resolution":   "1220x686"
```

所以在 1220×686 上量到行距 70px，换到 1920×1080 会自动变成 110px。
**删掉 `预设/` 目录才会要求重新标定**，删 `输出/` 不会——启动时它会拿预设补上并顺手写回本机配置。

### 手动框选（备用）

界面右下角还有 **手动框选（备用）**，走的也是同一套"中位数 + 吸附 + 试拍"，只是入口在浮层外面。
浮层打不开（比如游戏全屏独占）时才需要它。

## 昵称库：上几次的结果就是这一轮的先验

公会名单有个天然性质：**成员几乎不变**，一轮下来只有一两个人进出。所以"上次采到的那批名字"
对这一次就是最硬的先验——同一个人在同一台机器、同一套字体渲染下，读歪的方式也是固定的：

| 正确写法 | 偶尔读成 | 相似度 |
|---|---|---|
| 非洲晒太阳 | 非洲吧太阳 | 0.80 |
| 村里响当当 | 村果响当当 | 0.80 |
| 博麗霊夢 | 博麗需夢 | 0.75 |
| HANSON | NANSUN | 0.67 |
| 命OVO | 命UVU | 0.50 |

**库只是补充，不是判据。** 这条界线是硬划的：

- **识别不看库**：`scan()` 一个字都不改，OCR 读到什么就是什么
- **判定不看库**：`same_row` / `rarer` / 位置合并 / 收工复核，全部只认 OCR 原文和
  "同一物理行"这个位置证据。库里有什么都不影响它们
- **只在收工对一次账**：采集全程库只记候选，跑完一整趟才用
  **"这个写法全程出现过几次"**这个硬证据定案

为什么一定要放到最后：采集途中任何一刻的证据都不够。一个名字只在某一屏露过一次，
你没法判断它是"读歪的老成员"还是"只露了个面的新成员"；而跑完一整趟，出现过
**两次以上的一律当真成员**——库碰都不许碰。这条是"库不许影响相似名称判定"最硬的闸。

它补的是"位置合并"的盲区。位置合并要求同一行在相邻两屏都出现过，可一屏最上面那一行
往往只被扫到一次（下一滚就出去了），读歪就没有第二次机会——实测顶行误读率 2.7%，
是其余行的近两倍。库对账不需要第二屏。

**七道闸，全部满足才归位**（任意一条不过就原样保留）：

| # | 条件 | 挡的是 |
|---|---|---|
| 1 | 字面不在库里 | 老成员本来就不该改 |
| 2 | 没参与过任何位置证据（`_links`） | 位置说过话的，位置说了算 |
| 3 | 不在本屏与上屏的对齐区间里 | 那几行有位置证据兜底 |
| 4 | 全程只被读到过 **1 次** | 出现两次以上 = 真成员 |
| 5 | 库里恰好一个够格的候选 | 公会真有近名成员时，猜哪个都错 |
| 6 | 那条候选在库里已稳定 ≥ 2 轮（或标了 `seeded` 的基准条目） | 本轮刚进来的新人没资格吸别人 |
| 7 | 那一屏里没有第二个位置出现过这条候选 | 同屏两个都在 = 两个真人 |

再加两道字面闸：

| 情况 | 处理 | 原因 |
|---|---|---|
| 两个字的昵称 | 不做模糊比对 | `空本`/`空木` 是同一行读歪，`大白`/`萧白` 却是两个真人，相似度都正好 0.5，光看字面分不开 |
| 相似度 0.50~0.62 | **只说不动** | `命UVU` 对 `命OVO` 只有 0.50，这个区间分不清"同一个字读歪"和"两个近名真人"。名额照留，日志里点名，让你自己核一眼 |
| 书写系统不一样 | 不动 | `命OVO`（汉字+字母）和 `DORO`（纯字母）等长、相似度恰好 0.5，不可能是同一个字读歪 |

所以"多出一个名字"和"少一个真成员"之间，工具永远选前者——**丢数据比多算严重得多**。

### 每轮结束会说清谁进谁出

```
本轮 32 人 · 库内 33 人 · 新增 1 人（新来的） · 上次有这次没见到 1 人（老张）
```

"上次有这次没见到"**不会立刻删库**——中途停下的那轮少人太正常了。要连续 2 轮
**完整采到列表末尾**都没见到，才认为真的退会了。中途停下、或名单不到 3 人时，一律不判退会。

界面上点 **昵称库** 能看到库里现在有谁、每个人被采到过几轮、记下了哪些误读写法。

### 成员变动：谁走了、谁是新来的

单看昵称库那张表回答不了"是哪一轮变的"——它只留**最后一次**出现时间。所以每轮收工
会往库里写一行变动记录，点 **成员变动** 按轮次倒着列：

```
时间                 采到  新增  未见  移出  状态
2026-10-30 14:18      32    1     1     —    有变动
2026-10-29 20:04      18    1     —     —    未采完   ← 整行压暗
```

选中哪一行，下面就把那一轮说清楚：新来的、没见到的、已移出库的、归位了几处误读写法。

三条规矩都是为了**别把"没采到"说成"退会了"**：

| 规矩 | 为什么 |
|---|---|
| 没采完的那轮不参与判定 | 中途停下少几个人太正常，拿它算退会能把整张名单判成"都走了" |
| 连续 2 轮完整采集都没见到才移出 | 一次没见到可能只是漏采或误读 |
| 移出必须写进收工摘要 | 移出是不可逆的（下次进来会被当新人），不能只埋在日志里 |

还有一条只提示、不动作的：**上一轮恰好 1 进 1 出**时，会标一句"可能是改名"。
公会里改名远比"走一个又来一个"常见，但库是按名字认人的，改名在库里看起来就是一进一出。
工具只提醒，绝不自动合并——真走了人又来了新人时，自动合并会把两个人的记录搅在一起。


### 库同时也是字库：读歪的规律反过来能验证读歪

把库里攒下的误读写法逐位对齐，就得到这台机器、这套字体的**易混字表**（窗口底部会直接列出来）：

| 读歪的字 | 正确的字 | 来自 |
|---|---|---|
| U | O | 命OVU → 命OVO |
| 吧 | 晒 | 非洲吧太阳 → 非洲晒太阳 |
| 果 | 里 | 村果响当当 → 村里响当当 |

这张表**不进任何门槛、不参与任何合并**，它只决定提示语怎么说。同样是"相似 0.50 不够、
没自动归位"，现在分三种说法：

| 差异情况 | 日志怎么说 | 给人的判断 |
|---|---|---|
| 全是已知易混字 | 像这台机器字体的老毛病 | 大概率该删 |
| 有从没见过的字 | 更像两个真人 | 大概率别动 |
| 库还没攒下记录（冷启动） | 字面判断不了 | 老实承认没证据 |

### 两种"库有话说、但不许改名单"的情况会被点名

1. **同屏双疑似**——同一屏里两个相似写法各占一行（例：`命OVO` 和 `命UVU`）。同一屏不可能
   把同一个人读两遍，**除非那一行被行切分切成了两段**；真是那样就该去修行切分，而不是
   改名单。工具把这对名字和相似度摆出来，怎么处理你定。前缀只露 1 屏和每屏都在，措辞不同：
   前者八成是切分抖了一下，后者要么是两个近名真人，要么切分固定多切了一块。
2. **孤行可疑**——某个野名字全程只露过 1 屏，却和库里一位稳定出现（≥3 屏）的老成员只差
   易混字。位置证据（相邻两屏同一行）没对上，`_merge_misreads` 和 `_reconcile` 都没资格
   并它，但它八成就是读歪的——点名让你自己删。

这两类**只写日志、名单一个字都不动**，也不再像早期版本那样静默丢弃。完整采集一趟如果
本来就干净（32 人就 32 人、无跳行），它们一条都不会出声——实测 184352 那 27 屏全程零提示。

**字面相似度低于 0.50 的两条，工具根本不会把它们联系起来**（`命YUY` 对 `命OVO` 只有 0.25），
所以那类读歪连"可疑"都不会报——这不是漏了，是字面上确实没有任何线索。确定是同一个人的话，
直接手工加 `alias`（见下节），别名不受门槛限制。

### 库会自己长大，不用手工录

每轮结束时，凡是**被位置证据钉死**的读歪（同一物理行、屏数差一倍以上的那对写法），都会自动
写进正确写法名下的 `alias` 数组。下一轮 `roster_cand` 靠别名直接命中，相似度按 1.0 算，既不走
模糊比对，也不受"库里至少稳采 2 轮"那条限制——别名比模糊比对硬一档。

从空库跑一遍 184352 那 27 屏，一轮就攒下 3 组：

```
非洲吧太阳 → 非洲晒太阳      村果响当当 → 村里响当当      命UVU → 命OVO
```

有了这几条，第三次故意制造"跳行"（位置证据完全失效、`same_row` 只有 0.5 的那种）也能把两个
幽灵精确归位：10 人回到 8 人。**这就是"多跑几轮识别率会变高"的具体机制**，不需要你做什么。

想手工补一条也行：打开 `预设/昵称库.json`，在正确写法那条记录的 `alias` 里加上读歪的写法，
下一轮直接生效。**别名按 1.0 算，不受 0.50 / 0.62 这些相似度门槛限制**——所以连"字面已经
不像、工具判断不了"的那类也能手工救回来。

```json
"命OVO": { "first": "...", "last": "...", "rounds": 6, "miss": 0,
           "score": 0.99, "alias": ["命UVU", "命YUY"] }
```

工具目录里已经带了一份初始库（32 人基准，每条标了 `seeded`，可以直接参与对账）。
想从头建也行：点【昵称库】→【清空昵称库】，之后跑一轮就自动建起来，那一轮不做对账
（没有先验可用），从第二轮开始生效。

## 伤害记录（联盟突袭）· 第二个场景

工具行里的【伤害记录】打开一个独立窗口（`600×820`），采的是：

```
联盟 → 联盟突袭 → 联盟记录 → 「今天」页
[LEVEL 10] HANSON      2,158,171,750   ← 一行 = 一次出击
           ⚔ 古铁        0.0%
```

| 字段 | 从哪来 | 说明 |
| :--- | :--- | :--- |
| 天 | 列表里的「第N天」标记 | 滚动后标记会滚出画面 → 用上一个已知的天往后补；开头就没标记会告警 |
| 成员 | 伤害左边的昵称 | 与名单场景同一套合法性校验 |
| BOSS | 成员名正下方 | **必须单独抠图重认**，见下 |
| BOSS 等级 | 左边的 `LEVEL N` | 无空格也能认（`LEVEL9`） |
| 伤害 | 右侧大数字 | 千分位格式校验，不合格标 ⚠ 不硬凑 |
| 占比 | 伤害正下方 | 实测样本 6 行全是 `0.0%`，语义未确认，原样存 |

**先选期数**：工具窗口顶部有「期 S19」下拉。国服每期只有 **5 个固定 BOSS**（S14~S39 全表在
`预设/盟战boss表.json`），选对期数后 BOSS 名会被归一到这 5 个标准名——`本铁匠`→`铁匠`、
`感医师思`→`医师`、`火神`（不是本期）→留空。这是校验名字最硬的一道闸，比调几何可靠得多。

**每期每人每天 3 刀**：收工时若有人记录数 >3，日志会点名（大概率是重复行），普通/困难模式
只影响实际出刀数，不影响解析。

**用法**：游戏里手动开到联盟记录页 → 点【采集本屏】确认一屏认得对 → 点【开始】整页滚采 →
【导出明细】/【导出汇总】。导出落在 `输出/伤害记录_*.csv`、`输出/伤害汇总_*.csv`。

**滚采怎么走**：点【开始】后，工具按"截图 → 认出本屏 → 和前屏对齐 → 追加新行 → 滚一屏 → 等停稳"循环。
每次滚动默认往下走 2.5 行，留出重叠区做核对；位移量不出来或重叠区对不上时**不追加**，
连续两次失败就换一种滚动方式（拖动 → 滚轮 → 翻页键），三种都试完才收工。
日志里每条 `拼接 +N 条（位移 M 行，重叠核对 x/y）` 都是这次对齐的证据。

**自动进入（不用手点页面）**：停在联盟页或联盟突袭页，点【自动进入】——
现场截图 → OCR 找「联盟突袭」卡片 / 「联盟记录」按钮 → 点字的中心。
**不写死任何坐标**，所以窗口位置、大小、UI 缩放都不影响（坐标是当场从画面里读的）。
每一步都校验页面真的换了；换不过去就停住并说明停在哪一步，绝不接着乱点。
前提：游戏窗口得在前台（点按钮时会自动提前台，失败会提示你先点一下游戏）。

**先标字段（换窗口大小/改 UI 缩放后必做）**：点【标定字段】，弹窗里只显示放大后的列表区域，
依次拖三个框：① 红色 LEVEL 徽标（贴着画）② BOSS 名称 ③ 百分比。存进 `预设/伤害记录预设.json`
的 `fields`，单位是**成员名字高的倍数**（不是像素）——所以换分辨率、改 UI 缩放都自动跟着走。

字段框锚在「成员名」上而不是整屏，因为列表会滚、行位置是变量，但「等级在名字左上 3 个字高」
这件事不变。默认值来自 2320×1305 真机帧实测，不标定也能用；标定是给你换环境时用的。
前提：这一屏得先认出成员名（列表要露出来）。

**再圈范围（可选）**：点【圈选范围】，在截图上拖一个框把**整块记录列表**框进去。
存进 `预设/伤害记录预设.json`（存的是相对整屏的比例，换分辨率自动换算），之后每次采集
只在这个范围里认字——标题栏、搜索按钮、其它卡片一律不参与。不圈也能用（全屏识别）。

**认不准的时候点【诊断帧】**：把最近一屏的原图、每张卡片的框、四个字段的裁图存进
`输出/诊断_伤害_<时间>/`（`卡片.json` 里是全部坐标）。等级认不到时工具会**自动存一次**，
所以只要跑过一轮，现场证据就在。

### 为什么不自动点进联盟记录

本项目的铁律是"不盲点"：联盟突袭卡片、联盟记录入口这两处的按钮位置**没有实测样本**，
在没认出来的页面上试点，是唯一可能造成实际损失的动作。所以这一版把进页面这一步交给人，
工具只负责"页面露出来之后"的采集。等拿到那两个页面的截图再接导航状态机。

### 三个和名单场景不一样的地方

1. **BOSS 名不能靠全屏检测**。白字压深色卡面、左边还挨着 BOSS 小图标，实测 det 6 行漏 3 行
   （古铁 / 铁匠 / 医师）。改成"det 只找行 → 每个字段抠 ROI 单行识别"后 6/6 全中（0.98~1.00）。
2. **伤害数字要读两遍**。同一块 ROI，`up=1` 读对、`up=2/3/4` 读成 `2,158,17,750`（少一位），
   而置信度是 0.997 —— 光看分数会被骗。所以按千分位规则校验，多倍率投票，冲突就标存疑。
3. **去重不能看内容**。同一成员对同一 BOSS 打出同一伤害是常态（样本里 HANSON 两次都是
   2,158,171,750），所以只认位置证据：像素位移算"走了几行" → 再用重叠区内容核对；
   位移因行距相等会混叠（272px 被量成 182px），所以允许 ±1 行修正，修正也救不回就停。
4. **等级：徽标框的下边界原来切掉了徽标下半截**。用真机 2320×1305 帧逐行量：徽标实际
   偏移是「左 -3.1h、上 -0.55h、右 -0.1h、下 **+1.0h**」，旧代码写的是 `+0.6h` ——
   下半截被切掉，`10` 自然读不出来。改成实测常量后，还要两步：把徽标里除白字以外的东西
   全去掉（卡片白边与字同为白色，用「是否连到框边」区分），再放大 6 倍识别；最后
   **8 个裁切组合投票，凑不齐 2 票就留空标存疑**（`1` 和 `10` 猜错的代价太大）。
   实测 573 / 2092 / 2320 三种分辨率全对。
5. **等级靠颜色找、不靠比例猜**：红底白字是画面里唯一的大块红，定位它不需要任何比例假设。
   **试过"圈一张卡再按比例切五个字段"，实测不成立**：手画框抖 6px 就会把
   `2,158,171,750` 切成 `2,58,171,750`、BOSS 名带上图标残字（`巡邪魔`/`愿重装火神R`），
   所以圈选只用来框"整块列表"当搜索范围，字段定位交给颜色锚点和 det。
6. **BOSS 名先按亮色墨迹列收框，再识别**。图标挨着名字，框切到它就多一个字
   （真机出过 `感医师思` / `惠医师` / `本铁匠`，同一个框挪 1px 结果就跳）。
   现在用"按列分组取最宽的一组"把图标挑掉（和名单找昵称同一套思路，判据换成亮像素），
   收到紧框后单行识别就够（实测 6/6，20ms）；紧框读不出才上 det，仍是垃圾串就表决。
7. **被列表边切掉半截的行直接丢弃**。拖动滚动不对齐整行，最上/最下一行常常只露半截，
   BOSS 行已被裁掉（真机出过 BOSS=`_`、占比空）。这种行在相邻屏一定完整出现过，
   丢掉让拼接处理。半行判据：成员名字高 < 本屏中位数 × 0.65。
8. **认不出的 BOSS 名留空，不写垃圾串**，并在窗口台账记"存疑"、自动存诊断帧。
   `本铁匠`/`_` 这类宁可空着让你手补，也不要混进导出。

### 外部识别（可选，默认关闭）

本地用的是 PP-OCRv6 **small** 模型，14px 字高的小字就是它的极限。要更强只能外接后端，
所以留了一个**可插拔的外部识别桥**：`raid_cli.py` + `预设/识别后端.json`。

- **只在存疑时调用**：本地投票凑不齐 2 票、或 BOSS 认不出，才把那一小块裁图交给外部命令；
  正常行完全不碰它，滚采速度和成本不受影响。
- **后端无关**：任何「输入一张 PNG、stdout 输出文本」的命令都能接，换 `cmd` 即可，不用改代码。
- **失败静默降级**：超时/报错/输出垃圾一律当「没认出来」，连续失败 3 次本次运行自动停用。

配置示例（`预设/识别后端.json`）：

```json
{ "enabled": true,
  "cmd": ["D:/Tools/Umi-OCR/UmiOCR.exe", "--path", "{png}"],
  "timeout": 15 }
```

现成三条路：

| 后端 | 特点 | 配置 |
|---|---|---|
| **Umi-OCR** | 本地免费、中文强，自带 CLI | 装好后把 `UmiOCR.exe` 路径填进 `cmd` |
| **PaddleOCR CLI** | 本地、可换 server 大模型 | `python -m paddleocr ocr -i {png}` |
| **视觉模型**（VLM） | 小字最稳，但要 key/联网 | 用工具自带的 `外部识别_vlm.py`，设 `SILICONFLOW_API_KEY` 等环境变量 |

`外部识别_vlm.py` 是现成脚本（支持硅基流动 / OpenAI / 通义 三种 OpenAI 兼容端点）：

```json
{ "enabled": true,
  "cmd": [".venv/Scripts/python.exe", "外部识别_vlm.py", "{png}"],
  "timeout": 30 }
```

## 困难模式（第二客户端 · demo）

困难模式的「联盟记录」和普通模式不是同一套界面：日期栏是横向 tab（`第 1 天 / 第 2 天 HARD`）、
等级徽标恒为蓝色 `LEVEL 1`（没有信息量）。所以单独做了一个客户端 `hard_client.py`，
**暂不并入 `raid_*`**，等正式客户端那一轮再合并。

| 项 | 值 |
|---|---|
| 启动 | 桌面 `NIKKE困难采集.bat`（GBK + 自提权 + pythonw），或 `python hard_client.py` |
| 离线自测 | `python hard_client.py <样张.png>` → 期望「完整 6/6」 |
| 纯逻辑测试 | `python hardtest.py`（20 项，秒级，不弹窗） |
| 输出 | `输出\困难伤害_YYYYMMDD_HHMM.csv`：序号 / 成员 / BOSS / 伤害 / 剩余血量 / 置信度 |

**跑法**：接窗口 → 框选（框住卡片列表，别框进日期 tab 和滚动条）→ 采集本屏确认认得对 → 开始滚采 → 导出。

三点必须知道：

1. **要管理员权限。** 游戏以管理员运行时，普通权限进程拖不动（截图识别都正常，只是画面不动）。
   窗口里有【以管理员重启】。
2. **置信度是三者最低分**（成员/BOSS/伤害），不是平均分。低于 0.6 建议人工抽查。
3. **拖动速度固定 3px/28ms**。不要加"自动试速度"——实测会选中松手惯性途中的读数，
   后面重叠核对会整段失败（代价是一轮白采）。

**已知**：点【一键进记录】可自动从联盟页点到联盟记录页（复用 `raid_nav`，按文字锚点现场找，
找不到就停、不盲点），进页面后自动跑一次「采集本屏」校验。真机验证中，异常时仍可手动进页面。

## 它是怎么认的

四层，缺一层都掉准确率（实测依据见 `../04-复用方案/联盟名单采集-可行性.md`）：

1. **纵向投影切行** —— 只用「低饱和 + 中深灰 + 非纯黑」的像素做投影，彩色横幅和头像极黑描边不参与
2. **行级文字色过滤** —— 每行估一个文字色，昵称实测落在 62~84，玩家横幅是 5/9/15/35/无值，直接排除
3. **只跑识别不跑检测** —— `use_det=False`，单行 20ms。带上检测会在某些 ROI 高度整段漏检（这是原来"准确率低"的头号原因）
4. **格点拟合 + 昵称合法性** —— 昵称必然等距排列，不在格点上的丢；再过滤纯数字、含 4 位以上数字、UI 词

## 已知限制

- 32 人要滚 24 步（每次 1 行），**每滚一次首行 y 会变**，但工具按名字而不是序号记录，滚动不影响去重
- 名字序列的位移测量有天花板：两屏完全没有重合行时，"刚好一屏"和"跳过几行"无法区分。工具靠闭环步长把这种情况压到几乎不出现（每屏 5 行时每次只走 1 行，恒留 4 行重合），一旦出现就立刻停并压低步长，不会静默继续
- 拖动方式**有误触风险**：起手点固定在采集区中央，会压在某个成员卡片上，个别版本可能识别成点击并弹出成员详情（试滚时会按 ESC 收掉）。真遇到就把 ROI 上沿抬到行间空白，让起手点落在两行之间
- 光标会被工具挪到采集区外避让（否则悬停高亮和箭头本身都会污染识别），采集结束后自动还回原位；**采集期间请不要自己动鼠标**，动了会被下一次截图当成画面变化
- 昵称去重按文本 + **行位置**两道并用：同一个昵称在相邻两屏被读成两种拼写时（`非洲晒太阳`/`非洲吧太阳`、`命OVO`/`命UVU`、`村里响当当`/`村果响当当`），工具按"两屏重合区间内同一物理行"把它们并回一个人，所以不会因为你认错字就多出一号人。留哪个拼写看**整趟采到过多少屏**（读错是偶发、读对是每屏都对），收工时再复核定一次。但**同一联盟真有两个人昵称只差一个字**时，它们会分别落在不同的行号上，不会被误并；反过来，如果同一联盟有人昵称完全一致，仍然只能记一条——导出后建议人工核一遍。
  上面两套判据都有盲区（实测漏网过「腊目夜」和「入魔工」），所以最后还有一道硬约束：
  **采到的名字比页面上写的人数多时，按"出现屏数最少"裁到一致并点名**——真成员每屏都在，误读只闪一两次
- 昵称库能救「读歪的字」，但救不了「读丢的字」：库只知道该有谁，不知道这一屏该有几行。整行被切碎（如早期的 `马三一`）由行切分那层解决，库这一层不参与
- 相似度 0.50~0.62 的读歪（如 `命UVU` 对 `命OVO`）**库刻意不救**：那个区间靠字面分不清「同一个字读歪」和「两个近名真人」，自动改就有可能吞掉一个真成员。工具会在日志里点名，并说明这次差异像不像本机字体的老毛病，你核一眼再决定
- 字库那层（易混字对）只能**解释**读歪，不能**证明**读歪：它来自过去确实发生过的误读，所以"差异全在已知易混字里"也只是提高了可能性，不等于结论。真要靠它坐实，只能人工核过之后由下一轮的别名机制记住
- 昵称库是**跟着工具目录走**的（`预设/昵称库.json`）。换电脑、发给别人用时，想带上先验就把这个文件一起拷过去；不带也能跑，只是头一轮没有纠错能力
- 轮次变动只留**最近 24 轮**（`ROSTER_HISTORY_MAX`）。再往前的人数与进出记录会被丢掉，名单本身不受影响。要更长历史就改这个常量——每轮几十字节，留着不心疼
- 变动视图里"可能是改名"只是**提示**，工具不做合并：公会里真出现"走一个又来一个"时，合并会把两个人的记录搅在一起，而拆开比合并便宜得多
- 游戏重启后窗口句柄会变，但**不用管**：工具每 2 秒在后台重扫，客户端开起来就自动接上（比例一致时连带上次标定一起带出）
- 游戏改版导致昵称配色变化时，改 `alliance_ocr.py` 里的 `TEXT_COLOR = (50.0, 115.0)`
