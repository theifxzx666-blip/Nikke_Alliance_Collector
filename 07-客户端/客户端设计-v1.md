## 1. 技术选型

### 1.1 本机事实（已核实，非推断）

| 项 | 值 | 来源 |
|---|---|---|
| 系统 | Windows 11 家庭版 中文版，Build **26200** | `Win32_OperatingSystem` |
| 现有引擎 | Python 3.12.13 + RapidOCR(onxx) + ctypes 注入，已跑通两条产线 | `05-工具/.venv` |
| PySide6 可装 | **6.12.0**（阿里镜像，另有 6.11.x / 6.8.x） | `pip index versions` |
| Qt 的 Windows 支持 | **Windows 10 1809 或更高**；且官方注明 **6.12 是最后一个支持 Win10 的版本** | doc.qt.io/qt-6/supported-platforms.html |
| 现有 UI | tkinter，无法做毛玻璃/圆角/阴影 | `hard_client.py` |

### 1.2 候选对比

| 方案 | 复用引擎 | 视觉保真 | 交付复杂度 | 结论 |
|---|---|---|---|---|
| **A. PySide6（Qt6）单进程** | 100%（同进程 import） | 高：无边框 + 自绘模糊 + QSS | 低：一个 Python 工程、一套打包 | **选它** |
| B. WPF 前端 + Python 边车 | 100%（靠 IPC） | 最高（与 GM 工具同栈） | 高：两套构建、两套进程、端口/握手/守护 | 备选 |
| C. Electron / Tauri + 边车 | 100% | 高 | 高：体积 150MB+ / 需 Rust | 否 |
| D. tkinter 改造 | 100% | 低 | 低 | 否，做不出毛玻璃 |

**为什么是 A**：
1. 真正的资产是"判据 + 标定 + 拖动参数"，它们全在 Python 里；换语言等于把已验证的 32/32、19 条全部推倒重测。
2. 单进程 = 没有 IPC 时序问题（现在所有 bug 都是时序类的，别再引入一层）。
3. PySide6 的 `QGraphicsBlurEffect`/自绘模糊 + 圆角裁剪 + 高 DPI 缩放都是成熟能力，打包走 PyInstaller（现有 `打包.py` 可复用）。

**代价**：安装体积 +90 MB 左右；Qt 的样式系统需要自己定一套令牌（见 §4），否则会重演"UI 不统一"。

### 1.3 M0 技术验证（30 分钟，先做再写代码）

| # | 要验证 | 通过标准 | 不通过时的退路 |
|---|---|---|---|
| 1 | 无边框窗口 + 圆角 + 拖拽/缩放 | 150% 缩放下边缘不毛刺（本机实测） | 用系统边框 + 自绘标题栏 |
| 2 | 背景模糊 | 两种实现任一可用：① DWM `DWMWA_SYSTEMBACKDROP_TYPE=3`（Acrylic）；② 截桌面 → PIL 高斯 → 画成背景 | ②始终可用，直接采用（GM 工具同思路） |
| 3 | 150% DPI 下文字清晰（本机） | `QFont("Microsoft YaHei UI")` 不糊、行高正确 | 全用逻辑像素 + `AA_EnableHighDpiScaling` |
| 4 | PyInstaller 打包后能起 | exe 双击出窗口、模型路径正确 | 模型外置到 `预设/`，运行时按 `sys._MEIPASS` 找 |

> ②是保底方案：截图模糊不依赖系统版本，且能保证"文字压暗层"的一致性（GM 工具里那张 `BlurEffect Radius=18` + 85% 压暗就是这么干的）。

### 1.4 版本锁定与 Win10 兼容（用户明确要求）

| 项 | 决议 | 依据 |
|---|---|---|
| PySide6 | 锁 **6.12.0** | 官方 Supported Platforms：Win10 1809+；且 **6.12 是最后一个支持 Win10 的版本**，再往上 Win10 就没了 |
| 解释器 | 3.12.13（与现有引擎同版本） | 避免 RapidOCR/onnx 的二进制轮子不匹配 |
| 背景模糊 | **默认自绘高斯**；Win11 可在设置里改用 Mica | Win10 没有 `DWMWA_SYSTEMBACKDROP_TYPE`，不能只依赖系统能力 |
| 窗口圆角 | 自绘（`QPainterPath` 遮罩） | Win10 没有系统级窗口圆角 |
| 字体 | 微软雅黑 UI（Win10 自带） | 不依赖 Win11 新字体 |
| 缩放 | 100 / 125 / 150 / 200% 都要对 | **本机实测 150%（devicePixelRatio=1.5）** |

**抓背景的做法**：窗口显示**前**先抓目标屏幕矩形（此时窗口还没盖住它）→ 缩到 1/8 → 高斯 18px → 放大 → 叠 82% 压暗。
窗口移动 / 换屏 / F9 对齐后重抓一次；抓不到（被遮挡、远程桌面）就退回纯色 + 噪点。

| 验证项 | 结果 | 证据 |
|---|---|---|
| PySide6 6.12.0 安装 | ✅ | `D:\Codex\依赖\venv-client`（Python 3.12.13） |
| 无边框 + 半透明 + 自绘圆角 | ✅ | `D:\Codex\临时\m0\m0_窗口.png`，圆角干净 |
| 自绘高斯模糊 | ✅ | 抓桌面 → 1/8 → 高斯 2.4 → 放大，背后纹理可见 |
| DPI | ✅ **本机 150%** | 逻辑 1707×1067 / 物理 2560×1600，`devicePixelRatio=1.5` |
| `DwmSetWindowAttribute(38)` | Win11 返回 0；Win10 会失败 | 故**不依赖**系统 Acrylic |
| 关窗后残留进程 | 无 | `tasklist` 复查 |

**两条从这次手绘 demo 换来的教训（已升级为规范）**：

1. **手绘整页必然出这类错**：`_card()` 把画笔设成 `NoPen`，紧接着那行文字就直接消失；
   表格两行忘了 y 递增，叠在一起。**结论：只有背景层手绘，内容一律用 QWidget + QSS。**
2. **ImageGrab 的 bbox 是物理像素，Qt 坐标是逻辑像素**，必须 ×`devicePixelRatio`，
   否则截到的是左上角另一块区域（第一次就踩了，截出一片白）。

## 2. 产品框架

### 2.1 进程结构

```
单进程
├── ui/         壳层 · 页面 · 组件 · 主题令牌
├── core/       引擎适配：直接调用 alliance_ocr / hard_client / raid_nav 的既有函数
├── platform/   win32：找窗口、改尺寸、吸附、DPI、输入注入
└── data/       模型 · 预设 · 导出
```

**引擎边界原则**：`core` 只做"把 UI 参数翻译成引擎入参 + 把回调转成事件"，不复制任何判据。
现有 `alliance_ocr.py` / `hard_client.py` 里的识别与滚动逻辑原样复用；UI 单独长，稳定后再把 UI 从旧文件里摘掉。

### 2.2 状态机（两条线共用）

```
IDLE ──绑定成功──> READY ──点开始──> PREP(导航/拉顶/校验) ──> CAPTURING ──> DONE
  │                  │                    │                      │
  └──绑定失败──> NEED_ATTACH         失败→停在原地并说明      失败/取消→STOPPED(可续采)
```

规则：
- **任何一步失败都要说清"卡在哪"**，不吞异常（沿用 `RaidNav` 的既有风格）。
- `STOPPED` 保留已采数据，可以继续；`DONE` 才提示导出。
- 采集中禁止切换模式（按钮置灰），避免两条线程抢鼠标。

### 2.3 数据模型

```python
CaptureSession(id, mode, game_rect, started_at, ended_at, rows[], meta)
RosterRow(name, level?, joined?, note)                    # 名单
RaidRow(member, boss, damage, pct, conf, raw{}, flags[])  # 伤害
```
- `conf` 保留原始最低分，归一/补全过的行加 `flags`（如 `归一自「铁E」`），导出时可选附带。
- 导出：`名单_YYYYMMDD_HHMM.csv` / `伤害_YYYYMMDD_HHMM.csv`，UTF-8 BOM；同时写一份同名 `.json` 便于后续分析。

## 3. 界面尺寸与摆放

| 项 | 值 | 说明 |
|---|---|---|
| 客户端宽度 | **496 px**（可 460~1600） | 竖屏；初版 444、二版 468 都**实测不够**，见下方论证 |
| 客户端高度 | 初始 620，可自由拉伸 | 用户拖边缘即可，尺寸记进设置 |
| 贴边间距 | 8 px | 两个窗口之间留一条缝，不挡游戏边框 |
| 最小尺寸 | 460 × 560 | 再小表格就装不下了 |
| 并排预设 | 右侧（默认）/ 左侧 / 自动 / 不动 | 设置里选，F9 立即并排 |

**宽度实测（2026-11-07 改）**：444 时「星空下的神话」被省略成「星空…」——列宽按"平均内容"估的账不可靠。
改用真实最长内容重算：成员 6 汉字、BOSS「重装火神R」、伤害 14 位数字，六列合计 **442**，
加两侧 12 内边距 → 窗口 **468**。改完实测表格内容宽 442、列宽 `[26, 96, 86, 122, 58, 54]`，无一处省略。
教训：**列宽只能按最长真实样本定，不能按平均值**；定完必须用最长样本截图核一次。

**宽度再改（v1.1，2026-11-07 13:30）**：上面那组列宽仍然是"估"的——`QFontMetrics.horizontalAdvance`
不含 QSS padding 与样式 textMargin，逐列差 1~2px，于是「重装火神R」变成「重装火…」、
「100.0%」变成「100.0…」、「0.98」被切掉最后一位。改用 **`QStyledItemDelegate.sizeHint()`**
（Qt 自己算的"刚好够"）+ `QHeaderView.sectionSizeHint()` 定宽，实测需要
`[44, 92, 76, 116, 60, 48] = 436`，加边框与滚动条 → 窗口 **496**（视口 462）。
教训升级：**"按最长样本"还不够，要用 Qt 自己的 sizeHint；手算宽度必然差一两像素**。

## 4. UI 规范（唯一真源）

> 所有组件只允许引用下表令牌；**禁止在页面里裸写颜色/字号/圆角**。这条是"UI 不统一"的根因治理。

### 4.1 色板（沿用 GM 工具的毛玻璃画刷）

| 令牌 | 值 | 用途 |
|---|---|---|
| `--bg-scrim` | `rgba(16,18,22,.82)` | 背景压暗层（保证正文对比度，GM 工具踩过：只上模糊不压暗，白字糊） |
| `--surface` | `rgba(255,255,255,.07)` | 卡片底（=GM `#1CFFFFFF`） |
| `--surface-strong` | `rgba(255,255,255,.11)` | 主操作卡 / 选中行（=GM `#2BFFFFFF`） |
| `--border` | `rgba(255,255,255,.12)` | 1px 描边（=GM `#1FFFFFFF`） |
| `--text` | `#D6D9DE` | 正文 |
| `--text-dim` | `#8B9199` | 辅助 |
| `--accent` | `#2F6FD0` | 主按钮（沿用现有 `ACCENT`） |
| `--ok` / `--warn` / `--err` | `#45B076` / `#E0A030` / `#D9534F` | 状态 |
| `--blur` | 18 px | 背景模糊半径（=GM `BlurEffect.Radius`） |

### 4.2 尺寸令牌

| 令牌 | 值 | 说明 |
|---|---|---|
| 圆角 | **8** | 卡片/按钮统一（=GM） |
| 卡片内边距 | 12 | 主操作卡 14 |
| 间距 | 8 / 12 | 组内 8、组间 12 |
| 控件高度 | 按钮 32、主按钮 40、输入 32、行 30 | 统一，不许出现 26/28/34 这种"手工微调" |
| 字号 | 标题 13 semibold / 正文 12.5 / 辅助 11 | 数字一律 `Consolas 12.5`（等宽，避免抖动） |

### 4.3 三条红线（对应 GM 客户端的三个老毛病）

| 老毛病 | 机制级约束（不是"注意一下"） |
|---|---|
| **UI 不统一** | 只允许 `Theme.tokens`；页面里出现字面量颜色/字号 → 启动自检报错（开发模式直接弹） |
| **文本显示不全** | 所有文本控件强制 `ElideMiddle/Right + ToolTip=全文`；表格列宽 = `max(内容宽, 表头宽)` 且末列 `Stretch`；标题栏禁止放会变长的文本 |
| **组件显示不全** | 控件最小尺寸一律用 `sizeHint()`，禁止硬编码小于内容的宽高；**启动做一次全量布局体检**：遍历所有可见控件，`size().width < sizeHint().width - 1` 就写日志并在开发模式高亮 |

> GM 工具里真出过这事：WPF-UI 的 CheckBox 默认 `MinWidth=120`，塞进窄容器后右半边被裁。Qt 里的等价坑是 `QComboBox`/`QSpinBox` 的默认宽度，同样要在主题里统一收口。

## 5. 操作动线与快捷键

### 5.1 冷启动（用户只做一件事：开游戏）

```
启动客户端
  → 自动找回上次的游戏窗口（进程名 + 标题匹配）
      ├ 找到且 16:9 ✓ → 顶部绿条「已连接 · 1920×1080 · 16:9」
      ├ 找到但比例不对 → 顶部出「修正为 16:9」（一键，不需要进设置）
      └ 没找到 → 顶部黄条「未连接 · F2 重试」，同时列出候选窗口名（只列不自动连）
  → 自动吸附到游戏右侧（记住上次的预设位）
  → 进入 READY，大按钮写着「开始采集（F3 名单 / F4 伤害）」
```

**绑定逻辑细节**：默认绑定"上次那个进程名 + 标题正则"，命中多个取前台那个；
**换窗口/挑进程只在设置页**里做（用户明确要求把设置项移走）。

### 5.2 一次采集（以伤害为例）

```
F4 → PREP：一键进记录（RaidNav）→ 首屏识别校验 → 条数/字段达标
   → CAPTURING：拖动 → 停稳 → 识别 → 拼接（日志每屏一行）
   → 到底：用最后一屏回填 → DONE：19 条 / 9 人，提示「F7 导出」
```

对应按钮只有两个状态：**【开始采集 F4】** / **【停止 Esc】**。其余（本屏、框选、导出）是次按钮。

### 5.3 快捷键

| 键 | 作用 | 说明 |
|---|---|---|
| **F2** | 重新绑定窗口 | 找不到游戏时用 |
| **F3** | 名单采集 开始/停止 | 切换式，状态在按钮上显示 |
| **F4** | 伤害采集 开始/停止 | 同上 |
| **F5** | 采集本屏（不滚动） | 调参/确认用 |
| **F6** | 框选 / 标定（当前模式） | 只有当前模式需要的那个动作 |
| **F7** | 导出 CSV | 无数据时置灰 |
| **F8** | 置顶开关 | 默认开 |
| **F9** | 对齐窗口（按当前预设位） | 游戏窗口动了就按一下 |
| **F10** | 设置 | 打开右侧抽屉 |
| **F11** | 调试面板（默认隐藏） | 也可 `--debug` 直接开 |
| **Esc** | 停止一切 | 沿用现有习惯 |

> F 区冲突提醒：部分游戏会占用 F1/F11/F12，我们避开 F1/F12；F11 只在客户端有焦点时响应。

### 5.4 实时跟随最新（用户明确要求）

- 表格默认**跟随光标在最后一行**，新行进入时滚动到底 + 该行 300ms 高亮淡出。
- 用户手动上滚 → 暂停跟随，右下角浮出 `回到最新（3 条新）`；点它或按 `End` 恢复。
- 日志区同样跟随（现有 `Text.see("end")` 的行为），但要**只在用户没往上翻时**才自动滚。
- 表格用 model/view（`QAbstractTableModel`），200 行内无卡顿；不用 widget 堆行。

### 5.5 导出与默认路径（用户要求）

- 默认目录：`APP_DIR/输出`（源码态 = `05-工具\输出`，打包后 = exe 同级 `输出\`）。
  **与旧工具同一个目录**，两个前端导出的文件天然并排，不用来回找。
- 设置页「默认导出目录」可直接改，也可点「…」挑；写 `预设/导出设置.json`，键为
  `export_dir` / `last_export`，改完立即生效、不需要重启。
- 导出后底部常驻 **最近导出：`困难伤害_YYYYMMDD_HHMM.csv`** + 右侧【打开目录】
  （点开资源管理器）；鼠标悬停显示完整路径。启动时从设置里恢复，不用翻文件夹。
- 文件名沿用现状：`困难伤害_YYYYMMDD_HHMM.csv`，UTF-8 BOM（Excel 直接双击不乱码）。
- **日志只写文件名不写全路径**：完整路径会把三行日志挤成一行（实测 12:11 那次就是这样）。
- 缺字段的条目照常导出，但日志先点名「⚠ 第 [N] 条缺字段」——留空比编一个值安全。

### 5.6 快捷键形态（已定）

F3 / F4 是**切换式**：按一下开始，再按一下停止（与现有 Esc 语义一致）。
采集中按钮文字变成「停止 Esc」，图标由 ▶ 变 ■，避免"按了没反应"的错觉。

## 6. 两个窗口工具

### 6.1 强制 16:9

```
读取客户区 → |w/h - 16/9| <= 0.5% ? 什么也不做（明确提示"已符合，无需调整"）
否则：以宽度为准算高（或高为准算宽，取能塞进工作区的那边）→ SetWindowPos → 复验客户区
      → 复验失败（游戏自己又改回去）→ 回滚原尺寸 + 提示"该窗口不接受调整，请手动设置"
```
红线：**只改一次、只改游戏窗口、改完必须复验**；不复验的调整等于没做。

### 6.2 预制位置

- 预设：游戏右（默认）/ 游戏左 / 覆盖右下 / 不动。
- 计算：以游戏窗口所在的显示器工作区为界，贴边 8px；保证客户端完整可见（不被任务栏裁）。
- 游戏窗口移动/改尺寸后，F9 重新对齐；不做实时跟随（会跟游戏抢焦点）。

## 7. 调试面板（默认隐藏）

只在 F11 或 `--debug` 时出现，含：

| 区块 | 内容 |
|---|---|
| 拖动 | 速度参数、上一步位移/相关度、实际滚动行数 |
| 拼接 | 本次 k、重叠 hit/overlap、是否走补采 |
| 识别 | 每字段耗时、置信度分布、归一记录（如 `铁E→铁匠`） |

### 11.0 三条被判错的语义（先纠正认知，再改代码）

| # | 原来的实现 | 正确语义 | 影响 |
|---|---|---|---|
| A | 对齐 = 把客户端摆到游戏**旁边**，空间不够就贴屏幕右缘（**压在游戏上**） | 对齐 = **两个窗口并排、绝不重叠**；空间不够就先把游戏还原+缩到放得下 | 是"嵌入游戏里"的全部来源 |
| B | 页签只是换个标题文字，流程永远走 HARD | **页签就是流程**：伤害页 = HARD 滚采；名单页 = 名单采集 | 用户切到名单页按开始，跑的是伤害 |

### 11.1 切到名单页仍走伤害流程

- **现象**：切到「名单」→ 按开始 → 屏幕上滚的还是伤害记录。
- **根因**：`shell.py::_on_mode` 只改 `card_title/card_sub/btn_primary` 三个文本；
  `_toggle_run` 无分支，恒定 `self.engine.start()`（HARD）；`F3` 只做 `seg.select(0)`。
- **修法**：
  1. `_toggle_run` 按 `self._mode` 分派：`1 → engine.start()`；`0 → _open_roster_tool()`。
  2. 名单采集引擎仍在 `alliance_ocr.App`（Tk）里，**v1.1 不搬**（搬 = 重写
     `_tick/_apply/_after_scroll/_commit_roster` 一整条状态机，风险远大于收益）。
     名单页改为**诚实占位**：主卡写「名单采集在旧窗口完成」，主按钮写「打开名单工具」。
  3. `_open_roster_tool()`：源码态 `sys.executable alliance_ocr.py`；
     打包态找 `exe 同级\联盟名单采集.exe`，找不到就写出完整路径让用户去双击。**不静默失败。**
  4. 页签记忆：`预设/导出设置.json` 加 `mode`，启动按上次的页签落位（不再硬编码 1）。
- **验收**：名单页按开始 → 日志「已打开名单采集窗口」，鼠标一动不动；
  伤害页按开始 → 才走 PREP/滚采。重启客户端停在上次那一页。

### 11.2 在大厅不会进联盟主页

- **现象**：站在大厅（或任何非联盟页）点开始，直接报「当前页面既没有『联盟突袭』卡片也没有『联盟记录』按钮」。
- **根因**：`raid_nav.goto_record` 只覆盖「联盟概览 → 联盟突袭 → 联盟记录」，
  没有「大厅 → 联盟」这一跳，也没有「其它页 → 大厅」的回退。
- **修法**（全部复用名单采集**已实测**的页指纹与锚点，不新造坐标）：
  1. 页指纹（词表直接取自 `alliance_ocr.NAV_SPEC`）：
     · 大厅 `("方舟","大厅","物品栏","队员招募","作战出击","MISSION PASS")`，命中 ≥3
     · 联盟概览 `("日志","联盟公告","联盟功能","联盟射击场","联盟商店")`，命中 ≥2
     · 记录页沿用 `on_record_page`
  2. `goto_home()`：按 `ESC` 逐级回退，**每按一次都重新判指纹**，最多 5 次；
     一命中大厅立刻停（不许多按，多按会退过头）。
  3. `goto_record()` 新链路：
     `记录页? → 完事` → `联盟概览? → 点「联盟突袭」` → `大厅? → 点「联盟」`
     → `都不是? → goto_home() 再走一遍`。
  4. 点「联盟」：先在 token 里找归一化 == 「联盟」且中心落在
     `(0.935, 0.230, 1.000, 0.560)` 白名单内的，找不到才用实测锚点 `(0.970, 0.418)`
     （同 `NAV_SPEC[0]`）。**"找到词"和"允许点"是同一件事**，不给越界的口子。
  5. 每一步失败都写清卡在哪一句，不吞。
- **验收**：大厅起手能一路走到记录页；在一个无关页（如商店）起手，日志出现
  「按 ESC 回退（n/5）」并最终进联盟；ESC 到不了大厅时明确说「停在哪一页，请手动回大厅」。

### 11.3 窗口不能拉伸

- **现象**：只能拖标题栏移动，四边拖不动。
- **根因**：`Shell.__init__` 里 `setFixedWidth(T.WINDOW_W)`；无边框窗口没有边缘命中与缩放逻辑。
- **修法**：
  1. 去掉 `setFixedWidth`，改 `setMinimumSize(420, 560)` / `setMaximumSize(1600, 2000)`。
  2. 边缘热区 `HOT = 6px`（逻辑像素）：左/右/上/下 + 四个角，共 8 个方向；
     `mouseMoveEvent` 按方向设 `SizeHorCursor/SizeVerCursor/SizeFDiagCursor/SizeBDiagCursor`，
     离开边缘恢复 `ArrowCursor`。
  3. 按下在边缘 → 记录起始几何与全局坐标，`mouseMoveEvent` 里按方向算 `setGeometry`，
     并夹到 `minimumSize`；标题栏拖动只在**非边缘**区生效。
  4. 尺寸持久化 `win_w`/`win_h`；启动恢复（首次 = 468×620）。
  5. 缩放结束后 250ms 重抓一次背景（否则毛玻璃底会被拉花），抽屉按新尺寸重摆。
- **验收**：四边与四角都能拖；拖到最小停住；重启保持上次尺寸；拉伸后背景不模糊变形。

### 11.4 快捷键没反应

- **现象**：对着游戏按 F4/F9，客户端没动静。
- **根因**：`QShortcut(QKeySequence(key), self)` 默认 `Qt.WindowShortcut` —— 只有客户端有焦点才响应。
  用户 99% 的时间焦点在游戏里。
- **修法**：
  1. 新增 `app/hotkey.py`：`RegisterHotKey(None, id, 0, vk)` + `QAbstractNativeEventFilter`
     拦 `WM_HOTKEY(0x0312)`，`wParam` → 回调。
  2. 注册集：**F2 / F3 / F4 / F7 / F9 / F10 / F11**（与游戏常用键不冲突）。
     **Esc 不注册**（会劫持整个系统）；F5/F6/F8 属调试动作，只保留窗口内。
  3. 注册失败的键**逐个点名**退回 `QShortcut`（窗口内有焦点仍可用），日志写
     「F? 被占用，退到窗口内」——不许静默。
  4. 设置里给「全局热键」开关（默认开）；关掉后全部退回窗口内。
  5. 触发去重：全局注册成功的键**不再**建 QShortcut，避免一次按键执行两遍。
- **验收**：焦点在游戏里按 F4 能开始；日志出现「全局热键 F2/F3/F4…已注册（N 个）」；
  设置关掉后按 F4 无效（这是预期）。

### 11.5 序号 > 9 不显示

- **现象**：第 10 条起，`#` 列空白。
- **根因**：`TableModel.WIDTHS[0] = 26`。两位数宽约 15px + 单元格左右 padding 12 = 27 > 26，
  被裁掉；三位数更甚。属于 §4.3「列宽按平均值估」的同一个错，只是这次错在序号列。
- **修法**：
  1. 序号列宽 = `max(32, fm.horizontalAdvance(str(最大行数)) + 16)`，
     在 `_on_rows` 里当位数跨过 10 / 100 / 1000 时重设一次（只在跨位时改，避免每帧重排）。
  2. 序号列内容居中对齐，表头 `#` 同样居中。
- **验收**：造 120 行假数据，1~120 全部可见；第 9、10、99、100 条截图核对。

### 11.6 表头与内容列不对齐

- **现象**：表头文字和下面那一列的内容不在一条竖线上，越靠右越明显。
- **根因**：表头用 QSS `QHeaderView::section{padding:0 6px}`，单元格用
  `QTableView::item{padding:0 6px}`，但 **header 的对齐方式由 QSS/样式默认决定，
  与 `data()` 返回的 `TextAlignmentRole` 无关**；两者一旦不同源就是"各排各的"。
  叠加两个隐性因素：`setStretchLastSection(True)` 会改最后一列宽；
  列宽是写死的常量，没考虑表头文字比列宽长的情况。
- **修法**：
  1. 用 `hh.setDefaultAlignment(...)` + 每列 `setHeaderData(..., Qt.TextAlignmentRole, ...)`
     显式指定表头对齐；`data()` 里同时返回同一套对齐：序号居中、伤害/剩余/置信右对齐、
     成员/BOSS 左对齐。**表头与内容共用一张对齐表**（`TableModel.ALIGN`），不许各写一套。
  2. 列宽改成启动时实测：`width = max(hh.sectionSizeHint(i), delegate.sizeHint(idx) + 8)`，
     `MIN_W` 只作为下限兜底。**不要用 `fontMetrics().horizontalAdvance()` 手算**：
     它不含 QSS padding 与样式 textMargin，差 1~2px 就触发省略号（实测踩过两轮）。
  3. 最后一列不再 Stretch（Stretch 会让表头与内容在窗口变宽时不同步），
     改为 `ResizeToContents` 之外的做法：固定实测宽 + 右侧留白。
- **验收**：截图逐列比对表头文字中心与内容中心，偏差 ≤1px；窗口拉宽/缩窄后仍对齐。

> 实做时把第 3 条推翻了：最后一列保留 Stretch（它只影响最后一列自己的宽度，
> 表头与内容仍共用同一个 section 宽度，不会不同步），好处是窗口拉宽时右边不留死白。
> 真正要禁的是"前五列用 Stretch"。

### 11.7 对齐 ≠ 嵌入游戏窗口

- **现象**：点对齐后客户端**浮在游戏画面里**，看起来像嵌进去了；游戏一移动，客户端不跟。
- **根因**：两处。
  1. 游戏最大化（2274×1279）时，屏幕右侧只剩 ~280px < 客户端 468px →
     `plan_snap` 走"屏幕右缘"分支，**明知会盖住游戏也照样摆**（只在文案里警告）。
  2. 没有跟随：游戏窗口移动/改尺寸后没有任何监听。
- **修法**：
  1. 对齐语义改为「**并排不重叠**」。空间不足时按顺序：
     ① `ShowWindow(SW_RESTORE)` 取消游戏最大化；
     ② 以工作区为界算游戏的目标客户区：`gw = 工作区宽 - 客户端宽 - 间距 - 2*边距`，
        按 16:9 反算高；若高 > 工作区高，则改以高为准反算宽；
     ③ `SetWindowPos` 把游戏缩到该尺寸并贴左上（`SWP_NOACTIVATE`），**改完复验**；
     ④ 客户端贴游戏右侧 `gap` px。
     任一硬步骤失败（UIPI / 游戏拒绝缩放）→ **不对齐**，明确说「需要管理员/请手动缩小游戏」，
     **绝不退化成覆盖游戏**。
  2. 删掉「覆盖右下」预设（它就是"嵌入"的元凶），四个选项改为
     **右侧 / 左侧 / 自动（右满换左）/ 不动**。文案同步从「吸附」改成「并排」。
     （原稿写的是「游戏上方（横屏）」——实做时否掉了：竖屏客户端摆到游戏上方会挡住技能栏，
     而且大多数显示器上面没有空间。）
  3. 跟随：`QTimer` 每 600ms 读一次游戏客户区物理矩形，与上次不同 → 300ms 节流后
     重新对齐；设置项「跟随游戏窗口」默认开。跟随只移动客户端，**不抢焦点**
     （`SWP_NOACTIVATE`，且 `setGeometry` 不 activate）。
- **验收**：游戏最大化时点 F9 → 游戏被还原并缩窄、客户端在右侧，两者**零重叠**；
  手动把游戏窗口拖到别处，客户端 1 秒内跟过去；关掉「跟随」后不再动。

### 12.1 旧名单工具默认高度跟随客户端

- **现状**：`alliance_ocr.App` 硬编码 `geometry("620x940")`、`minsize(560, 800)`。
- **修法**：启动时读 `07-客户端/导出设置.json` 的 `win_h`（客户端持久化尺寸，当前 758）；
  读到合法值就 `geometry(f"620x{h}")`，读不到保持 940。宽度 620 不动。
  `minsize` 高度 800 → 700（否则 minsize 会把 758 顶回 800）。
- **验收**：旧工具启动后高度 = 客户端当前高度；手动拉伸旧工具不受影响（只动默认值）。

### 12.2 联盟突袭主页页面指纹（导航坑）

- **修法**：
  1. `which_page` 增加 `"raid"`：`on_record_page` 不中、但「联盟记录」token 命中
     （概览页没有该按钮，指纹安全；顺序在 record 之后、guild 之前）。
  2. `goto_record` 开头 `page == "raid"` → 不回退，直达「点联盟记录」分支
     （提取 `_enter_record()`，与概览→突袭后的路径共用）。
  3. `goto_home` 认出 raid 时打一条说明再继续 ESC（不再表现为"认不出"）。
- **验收**：navtest 新增 raid 指纹用例；站在突袭主页点开始一次直达记录页，不再绕回大厅。

### 12.3 场景A：成员名单录入并入客户端

- **原则**：名单判据状态机（`_apply/_reconcile/_roster_apply/_commit_roster`，几轮踩坑
  换来的六道闸）**一行不改**——不重写，headless 驱动 `alliance_ocr.App`。
- **新模块** `app/roster_bridge.py`：
  - Qt 主线程创建 `App()`（Tk）→ `withdraw()` 隐藏；`QTimer` 周期 `update()` 泵 Tk 事件

  - 采集走 `capture(auto=True)`；停止走 App 的停止接口。
- **细节调整**：
  1. 名单页主按钮 F3 = 开始/停止名单采集（不再拉起旧窗口）；`_open_roster_tool`

### 17.1 两页数据隔离（串数据的根因）

- **根因**：`self._rows` 与 `TableModel` 被两页共用。名单页把库成员塞进同一个模型后，
  切到伤害页只换了列头（6 列 / 3 列），行数据还是名单的；伤害采集再推数据时
  `_seen` / `scrollToBottom` 的基准也全乱了——表现就是"记录不滚动、内容对不上"。
- **修法**：两个真源 + 一个视图。
  - `self._rows_hard`：伤害采集的行（引擎 `_on_rows` 写入）
  - `self._rows_roster`：名单库视图（`_load_roster_table` / 引擎实时写入）
  - `self._rows` = 当前页签视图对应的那一份，只给现在的导出/按钮/副标题复用。
  - `_on_rows` 只在 `_mode==1` 时渲染；`_on_roster_rows` 只在 `_mode==0` 时渲染。
  - `_on_mode` 切页时用对应真源重建视图（伤害页恢复 `scrollToBottom`）。
- 采集中切页不打断：数据照常落到各自真源，切回来即见。

- `win.game_link(hwnd)` → `"gone" | "back" | "ok"`：

  杜绝两套文案。
- 三态文案（简短、书面）：

### 30.5 Win10 浅色主题白屏（用户真机截图）

**症状**：Win10 机器上设置抽屉整片变白，浅灰字几乎看不见；标题栏与其余页面正常。

**根因**：`QScrollArea` 的 viewport 是 Qt **自己内部建**的控件，`autoFillBackground=True`，
填的是系统 palette 的 `Base` 色。开发机深色主题是 `#2d2d2d`，Win10 那台是 `#ffffff`。
而整套配色是 `rgba(255,255,255,N)` 叠在深色底上的半透明层 —— 压在白底上就是白板，
文字仍是浅色令牌（`#D6D9DE` / `#8B9199`）→ 看不见。

**修法（两道闸）**：

1. `QApplication.setPalette(T.dark_palette())`，在**任何控件创建之前**。颜色与 QSS
   同源，一次覆盖 QScrollArea viewport、下拉弹窗列表、菜单、提示气泡这些 QSS
   按选择器管不到的内部控件。
2. `scroll.viewport().setAutoFillBackground(False)` + QSS
   `QScrollArea > QWidget > QWidget {{ background: transparent; }}`。

**验收方法**：`QPalette()` 默认构造会跟随本机（深色），测不出这个 bug —— 必须显式造
一套 Win10 浅色 palette（`Base=#ffffff`、`Window=#f0f0f0`）再建 Shell。
修复前抽屉中部像素 `#f0f0f0`，修复后 `#1b1e23`。

## 31. v1.24 规格（2026-11-07 20:45，Esc 停不住名单采集）

> 用户原话：我按 ESC 停止采集，但是页面还在一直进行操作。

### 31.1 症状

名单采集过程中按 Esc，界面毫无反应，游戏里还在自动点、自动滚。

### 31.2 三层原因（叠在一起才这么难看）

1. **Esc 监听根本没开**。`_set_running` 里 `esc.set_active(bool(run) or _continuous)`，
   `run` 来自 `state_sig`，而 `state_sig` 只播 `_continuous`。**导航那 5~20 秒里两个
   都是 False** —— 按 Esc 时轮询器是停的，`_on_esc_pressed` 一次都不会被调用。
2. **`stop_capture()` 不管导航**。只有 `if _continuous: cancel_auto()`，导航阶段
   等于空操作（`nav_to_members()` 里那套 `_nav_cancel` 是给"再点一次导航"用的，
   没接到停止按钮上）。
3. **最糟：导航一结束就自动开滚采**。`_poll_nav` 看到 `_nav_running` 变 False 就
   `_begin_auto()` —— 用户按停止，反而把采集"启动"了。

顺带挖出一处死代码：`_toggle_roster` 判 `self._bridge._busy`，而 `_busy` 是旧工具
`toggle_auto` 的旗标，客户端走 headless 路径**永远不设它** → 采集中再点主按钮
还是走"开始"分支，`start_capture` 又因 `_continuous` 直接返回 —— 按钮彻底没反应。

### 31.3 修法

| 位置 | 改动 |
|---|---|
| `RosterEngine.heartbeat` | `busy = _continuous or _nav_running` —— 导航期界面就该是"采集中" |
| `RosterEngine.stop_capture` | 置 `_cancelled`；导航中设 `_nav_cancel`；停 `_nav_timer`；滚采中 `cancel_auto()` |
| `RosterEngine._poll_nav` | 开头查 `_cancelled`，取消了就不再自动开滚采 |
| `RosterEngine._nav_done` | 覆写：收尾后**立刻** `_poll_nav()`，不等 300 ms —— 那一下会让 heartbeat 播"不忙"，界面闪一句"名单已存入" |
| `RosterEngine.start_capture` | 新一轮先清 `_cancelled` |
| `Shell._set_running` | Esc 激活条件加 `_nav_running`；收工提示只在真采到行时才说 |

### 31.6 全局热键的作用域（同一轮追加）

> 用户原话：优化下快捷键响应的范围 —— 只有在游戏的客户端以及工具的客户端内才能调用。

**问题不是"回调没判断"，是 `RegisterHotKey` 本身独占**：注册期间在浏览器、聊天框里
按 F3/F4，那个键既不给对方程序，又照样触发本工具的采集。在回调里 `return` 挡不住
独占，只会让"按键被吃掉"这件事更难解释。

**修法是按前台窗口动态注册/注销**：

- `win.in_scope(game_hwnd)`：前台窗口的进程 == 本进程（覆盖赞助/关于/设置等弹窗），
  或者根窗口（`GetAncestor(GA_ROOT)`）== 游戏 hwnd。判断不出来返回 `True` ——
  宁可多响应，也别把功能整个关死。
- `Hotkeys` 拆成 `install(binds)`（只记绑定）+ `set_scope(on)`（真正注册/注销）。

## 33. v1.26 规格（2026-11-07 21:15，伤害记录：BOSS 归一与置信度）

> 用户真机：伤害怕采集时 BOSS 名称没有按 boss 库核对，出现错名；部分行没填全；
> 置信度也不会更新。

### 33.1 三件事其实是两个缺陷

1. **出口那道归一从来没被调用。** `Engine._norm_rows()` 的注释写着「客户端比旧工具
   多一步：把 BOSS 名按本期表归一」，但 v1.0 起没有任何地方调它 —— 死代码。
   真正生效的只有 `read_hard` 里的 `raid_hard.boss_norm`
   （掐字 / 尾巴全等 / 首字唯一，阈值 0.6）。
2. **短名错一个字，两套规则都救不了。** `raid_core.match_boss` 的相似度阈值是 0.75，
   而两字 BOSS（邪魔 / 医师 / 铁匠 / 古铁）错一个字时 `SequenceMatcher` 只有 0.5；
   `boss_norm` 的 0.6 同样过不了。于是 `牙魔` 原样留在结果里。

「置信度不会更新」是第 1 条的副作用：名字被改过的行，`conf` 仍然是三个原始识别分数的
最小值，看上去和一眼读对的行一样可信。

### 33.2 修法

**① `raid_core.match_boss` 加「形近」规则**（闭集比对，放在相似度兜底之前）：

```python
if len(key) >= 2:
    near = [name for k, name in kmap.items()
            if k and len(k) == len(key)
            and sum(a != b for a, b in zip(k, key)) == 1]
    if len(near) == 1:
        return near[0], "形近"
```

等长 + 只差一个字 + 候选唯一 → 定人。实测 `牙魔→邪魔`、`医帅→医师`、`铁E→铁匠`、
`失匠→铁匠`；候选不唯一时不动，`乱写的东西` 仍然返回 `None`。

**② `Engine._norm_rows` 换成 `_finalize`，接到 `emit_rows` 上**：

| 步骤 | 做什么 |
|---|---|
| 闭集归一 | `match_boss(raw, 本期 BOSS)` —— 比 `boss_norm` 多认「包含」与「形近」 |
| 置信度如实下调 | `exact 1.0 / 包含 0.90 / 形近 0.60 / 相似 0.65`，取 `min(原分, 上限)` |
| 缺 BOSS 回填 | **同一成员在本份数据里只有唯一 BOSS** 时才填（一人打两刀不同 BOSS 是常态） |

`emit_rows` 是所有行（首屏 / 拼接 / 补全）的唯一出口，这一刀一定生效。
`_finalize` 只改传进来的副本 —— `capture` 内部还要拿原始行做 patch 判定，
那里的 `conf` 必须是识别分数本身，不能被降分污染。

### 33.3 为什么一直没发现

`hardtest` 只测 `raid_hard.boss_norm` 的字符串规则，不经过 `Engine`；`apptest`
也没有覆盖 `emit_rows`。**死代码不会有任何测试失败。**

## 35. v1.28 规格：内置复核 Agent（2026-11-07 21:55）

> 用户原话：性能优化这块，因为经常性有这些偶发的记录缺陷，能不能内置一个 agent
> 辅助强化识别成功率以及输出结果的清洗？

### 35.1 定位与三个约束

**不是替代 OCR，是在 OCR 之后用「记录之间的一致性」再查一遍。**

单条记录的错往往不是孤立的：伤害读错一位，就会和同一 BOSS 的其它记录差出量级；
成员认歪，名字就不在库里；血量读错，在同一（成员, BOSS）序列里就不单调。
这些矛盾**只有把整表摆在一起才看得见** —— 逐条看的时候每一条都"长得挺正常"。

| 项 | 选择 | 理由 |
|---|---|---|
| 形态 | **纯本地规则** | 离线、零配置，能连同 exe 一起发出去 |
| 时机 | **采集结束自动 + 导出前再跑** | 采完就知道有没有问题；导出用的是复核过的结论 |
| 处置 | **只标记不改数据** | 复核是提醒，不是替用户拍板；CSV 加一列「复核」 |

**为什么不接模型**：本项目的发布原则是离线单文件。把截图和盟员名单传出去，既违反
原则，也解释不清「我的名单传给谁了」。

### 35.2 七条判据

| # | 判据 | 触发条件 | 为什么可信 |
|---|---|---|---|
| 1 | 缺字段 | 成员 / BOSS / 伤害任一为空 | 最直接的缺陷，命中后不再跑其它判据（避免噪声） |
| 2 | BOSS 不在本期 | 归一后仍不在 5 个标准名里 | 一期盟战只有 5 个固定 BOSS，闭集是硬事实 |
| 3 | 血量不单调 | 同一（成员, BOSS）序列 ≥3 条且出现"两边都比它背离"的点 | 记录页按时间排列，同一刀的血量只会单向变化 |
| 4 | 伤害异常 | 同一（成员, BOSS）两条差 > 3 倍 | **不能跨成员比** —— 练度不同，同一 BOSS 差 2 倍是常态（实测 12.9 亿 vs 7.3 亿） |
| 5 | 重复嫌疑 | 同成员 + 同 BOSS + 血量相同 + 伤害差 ≤1% | 去重没合掉的漏网，完全相同也算 |
| 6 | 成员不在库 | 库非空 + 名字不在库里 | 新盟员或读歪，都要人看一眼 |
| 7 | 超过 3 刀 | 同一成员 > 3 条 | 困难模式一轮最多 3 刀；**只在第一次见到时报一次** |

### 35.3 输出

- **日志**：`复核：92 条 · 2 条可疑（重复嫌疑 1、超过 3 刀 1）` + 最多 6 条明细
- **CSV**：末尾多一列「复核」，写该行的全部可疑原因（`；` 分隔），正常的留空
- 没有可疑项时说一句「没发现互相对不上的地方」，不静默

### 35.4 用真实数据校过的误报率

拿 21:10 / 21:36 两份真实导出回放：

| 版本 | 复核结论 | 是否命中真问题 |
|---|---|---|
| 21:10（v1.25） | 3 条可疑：`#9 香装不在本期` / `#29 缺 BOSS/伤害` / `村里响当当 4 条` | 全部命中 |
| 21:36（v1.26） | 2 条可疑：`#9 重复嫌疑` / `村里响当当 4 条` | 全部命中 |

同一个 BOSS 差 3 倍"后误报归零 —— **判据的锚点选错，比判据不够更糟**。

## 37. v1.30（2026-11-07 22:15，同一份数据不能有两个说法）

> 用户真机 22:09 的日志里同时出现两句话：
> `⚠ 第 [57] 条缺字段（导出时会再点名）` 和 `复核：90 条 · 没发现互相对不上的地方`。

### 37.1 根因：补全只改了副本

`Engine.emit_rows()` 原来这么写：

```python
self.rowsChanged.emit(self._finalize([dict(r) for r in rows]))
```

`_finalize` 做了两件事——BOSS 闭集归一、缺 BOSS 按同成员唯一值回填——但都改在
**副本**上。于是出现两份数据：

| 谁 | 拿到的是 | 结论 |
|---|---|---|
| `capture` 收工自检 | 引擎原始的 `rows`（第 57 条 BOSS 仍是空） | 喊"缺字段" |
| 界面 / 复核 | 副本（已回填） | 说"没发现问题" |

导出时用的是界面那份，所以不会再报（日志里 22:10:20 确实没报）—— 但用户先看到的
是那句"第 57 条缺字段"，只能反复来问。

### 37.2 修法：补全落回引擎，降分只给界面

```python
def emit_rows(self, rows):
    hows = self._fill_known(rows)          # 原地补全，引擎也跟着变准
    self.rowsChanged.emit(self._apply_score(rows, hows))   # 副本降分
```

拆成两半，是因为两边要的不是同一样东西：

| | 要什么 | 为什么 |
|---|---|---|
| 引擎的 `rows` | **补全后的真实数据** | 收工自检、`patch` 判定都要它 |
| 发给界面的副本 | **按归一下调过的置信度** | 归一越勉强越不该跟读对的行同分 |

降分**不回灌**引擎：`patch` 判定拿 `nc > oc + 0.05` 比新旧读数，被降过分的数据
比出来就不公平了。

### 44.2 边缘行为什么一定会错

记录页一屏 6 行，每次滚 2 行。屏幕**首行被顶部日期栏压着、末行被底部渐变遮罩盖着**，
这两行在任何一屏里都是"半个头"：

| 症状 | 表现 |
|---|---|
| 名字读得到、BOSS 读不到 | `#65`：成员空、BOSS 位读成 `RT3` |
| 名字读到一半 | `が闹诊`（应为 `别闹`）、`EV3L2`、`RT3` |
| 血量读不到 | `MAO` 的 `#70`（`0.0%` 那组，血量空） |

**这是几何问题，不是分辨率、不是 OCR 精度。** 换个更好的模型也一样错 ——
被裁掉的像素不存在了。

### 44.3 解决思路：边缘行不作新数据来源，只作对齐锚点

一屏 6 行、滚 2 行 → **中间 4 行一定是完整的**，而且每行都会在相邻几屏里各出现一次。
所以：

1. 识别时给首行、末行打 `edge` 标记；
2. **`edge` 行只要缺任何一个字段，就丢弃**（不写进 `recs`）；
3. 它滚到中间那一屏时会被完整采到，一帧不落；
4. 列表到底时由 `_fill_bottom` / `_extra_read` 兜底补最后一行。

这样误差从"每轮 1~4 条"压到"0 条"，代价是每屏少两行候选 —— 但那两行本来就采不全。

### 44.4 表格不跟随的真实原因

```python
self.model.set_rows(disp)     # beginResetModel / endResetModel
...
self.table.scrollToBottom()   # 紧跟着调
```

模型刚 reset，视图的布局和滚动条范围都还是旧的，`scrollToBottom()` 滚了个空。
**推到事件循环再滚**（`QTimer.singleShot(0, ...)`）。

### 44.4 读歪的名字不再变成"新成员"

用户追加：识别到空白或不符合成员库的名称时，有时会被当成一条新数据处理。

`_commit_roster` 原来把本轮采到的**每个**名字都写进库。残读的名字
（`が闹诊` / `EV3L2` / `RT3`）只出现 1 次，也照样入库；下一轮它又变成"老成员"，
把模糊归位的门槛抬高 —— 越积越多（用户手动删过 `I-IXX`）。

**判据**：库外的新名字，整轮 `_hits ≥ 2` 才写进库。

- 真成员每屏都在，滚 2 行/次时至少被相邻几屏各见一次；
- 残读只在某一屏的边缘露一次，`_hits` 恒为 1。

⚠ `_hits` 有两个方向相反的消费者，别混淆：

| 消费者 | 判据 | 含义 |

| `_roster_apply` | `_hits < 2` 才归位 | 露过两次 = 真成员，不许改字 |
| `_commit_roster` | `_hits ≥ 2` 才入库 | 只露一次 = 残读，不许入册 |

```
正向：屏1 [0 1 2 3 4 5] → 屏2 [2 3 4 5 6 7] → … → 到底
反向：从底往回，屏N [6 7 8 9] → 屏N-1 [4 5 6 7] → … → 回顶
合并：两个方向按 成员+BOSS+伤害 去重；只在单侧出现的行标「只扫到一次」
```

代价：拖动次数 ×2（约 +90 秒）。收益：边缘漏采归零、残行会被另一方向覆盖掉。

## 46. v1.43 规格（2026-11-08 01:30，排序 + 严格模式反馈）

### 46.1 顺序和实机对不上

用户：**识别之后没有按实机记录排序，很容易出岔子。**

`rows` 的顺序是靠"采到的先后"攒出来的 —— 正常追加没问题（一屏一屏往下），
但三种情况会打乱：

| 情况 | 现在的行为 | 后果 |
|---|---|---|
| `补回 N 条被位移跳过的行` | `_dedupe(rows + lost)` → **追加到末尾** | 本该在第 3 条位置的行跑到第 90 条 |
| `patch` 修正边缘读数 | 按位置写回 ✓ | 没问题 |
| 严格采集补进的 3 条 | 追加到末尾 | 同上 |

日志里每条"补回"后面都跟着一条这样的错位。实机是按时间倒序排的，
一旦顺序乱掉，一眼就能看出不对。

**修**：补回时按它**在这一屏 `recs` 里的下标**插回去（`patch` 已经这么算
`base = len(rows) - len(last_rows)`，复用同一个基准）。

### 46.2 严格模式像闹着玩

日志只有两句，中间 38 秒全黑：

```
01:23:44  严格采集：从底部往回再扫一遍…
01:24:22  严格采集完成：这一遍补进 3 条
```

用户不知道它到底扫了几屏、扫到哪、有没有真的核对上。

**修**：

1. **每 5 屏报一次进度**：`严格回扫 5/26 屏 · 累计 97 条`
2. **收尾给结论**，说清"正向到底漏没漏"：

```
严格采集完成：回扫 12 屏 · 补进 3 条
→ 正向漏了 3 条，建议结算前都用严格模式
```

## 48. v1.45 规格（2026-11-08 02:00，排序仍错 + 回扫核对）

| 1. 大魔王·重装火神R | #2 | 后移 1 |

| 5. 非洲晒太阳·重装火神R | **#7** | 后移 2 |

### 48.1 `base + idx` 这个基准本身是错的

v1.43 用 `base = len(rows) - len(last_rows)` 算"这一屏在 rows 里的起点"。
它假设 **rows 的尾部正好等于上一屏的 recs** —— 可是补回的行一插进来，
`len(rows) - len(last_rows)` 就不再指向"这一屏起点"，越补越偏。

**改：用锚点法**（和严格模式回扫一致）。补回的一行，在**当前屏**里找它下面那一行，
拿那一行在 `rows` 里的实际位置当插入点：

```python
for nxt in recs[idx+1:]:                       # 屏幕下方的邻居
    anchor = next((j for j, x in enumerate(rows) if self._same_rec(x, nxt)), None)
    if anchor is not None:
        rows.insert(anchor, r); break
```

锚点在 `rows` 里的位置是**实际匹配**出来的，不依赖任何长度推算。
找不到锚点（这一屏整屏都是新的）才退回 `base + idx`。

### 48.2 回扫没核对底部、没校验、不跟滚动

```
01:49:25  严格采集：从底部往回再扫一遍…
01:49:28  严格回扫 0 屏 · 累计 96 条     ← 第一屏没采
01:52:22  回扫到顶（位移 0px）· 共 52 屏
```

三处：

1. **开始那一屏没采**：到底时画面就是最底部，回扫第一步先滚走了 → 底部那一屏
   从此没被反方向看过。**先采当前屏再滚**。
2. **没有重叠校验**：正向每屏都报 `重叠 4/4`，回扫什么都不报，无从知道对没对上。
   回扫也调 `splice` 报重叠。
3. **表格不跟着回滚**：界面一直停在底部。回扫时按当前扫到的位置滚动。

### 48.3 实机排序为什么重要

用户：**填入的信息错误时，能结合上下的记录锚定更正。**

顺序对了，错位一眼可见；《§48.1 的锚点法》本身也依赖顺序 —— 邻居找到了，
插入位置才准。这是整条链的地基。

## 50. v1.47 规格（2026-11-08 02:25，排序根治 + 残读相邻合并）

用户第三次说排序：**"修正完排序之后，遇到可疑的条目没结合上实机顺序去核对"**、
**"回扫每次划到底部都是滚一下再去识别，导致排序又乱套"**。要求"后续不要再犯"。

### 50.1 为什么 `_insert_in_order` 还是不够

锚点法要靠 `_same_rec` 找邻居。可**邻居本身可能读歪**（`小卡卜` 对不上 `小卡卡`），
找错了插入点，顺序就跟着错。

**根治**：不再推算插入位置，改成**记录每条"第一次被看到的屏号 + 屏内 y"**，
收工前直接排序：

```python
rows.sort(key=lambda r: (r["_pass"], r["_y"]))
```

滚 2 行、重叠 4 行 → 每条第一次出现的屏号**单调递增**（顶部的先被看到）。
同屏内按 y 排 —— 屏幕内的顺序是 OCR 直接给的，最可靠。

插入逻辑（`_insert_in_order`）保留作为中途显示用，但**最终顺序由排序决定**，
不再依赖任何"插到第几个"的推算。

### 50.2 残读相邻合并（`小卡卜` 那一条）

```
#94  小卡卡  医师        6,712,891,076  93.3%
#95  小卡卜  （无 BOSS）  0,712,091,076  93.3%   ← 同一条
```

`_same_rec` 判不出来：伤害差 8.4 倍（少读一位 `6`），BOSS 一方为空。

**新增两条判据**（都在同成员前提下）：

1. **后缀判重**：伤害位数差 1，且短串是长串的**后缀**
   （`712091076` 是 `6712891076` 的后 9 位 ✓）
2. **相邻残读**：剩余血量完全相同 + 名字只差一个字符 + 一方 BOSS 为空

第 1 条只在"位数差 1 且后缀"时成立 —— 之前七海那组 `930,162,509` vs
`8,938,162,509` 后缀不成立（前三位 `930` vs `938`），所以不会被误合。
