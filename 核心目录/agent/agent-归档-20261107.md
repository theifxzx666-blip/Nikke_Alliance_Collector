# agent.md — ArcanaHelper 客户端拆解

## 目标与结果

**目标**：拆解 `ArcanaHelper-V1.1.1.exe`，回答「文本采集原理 / 技术选型 / 为何快且稳 / 能否复用」，产物全部落在 `F:\Codex\Nikke\02_工位\10_数据管线\OCR采集`。

**结果**：静态逆向 + 关键环节实测全部完成，4 个问题均有证据级答案。

| 问题 | 结论 |
|---|---|
| 文本采集原理 | 本地无 OCR。链路 = DXGI 截屏 → 固定 ROI 裁剪 → 像素统计判 UI 状态 → 模拟点击 → 裁文本 ROI 存 PNG → **POST 到自己服务器识别** |
| 技术选型 | PyInstaller 6.x + Python 3.11 + customtkinter + dxcam + numpy/Pillow + pyautogui/ctypes + urllib |
| 快 | 固定 ROI 免滑窗（O(ROI)）、模板预处理缓存、DXGI 直出、上传体积极小、**重活外包服务端 GPU** |
| 稳 | 素材命名即状态机、带超时轮询、单次动作准入、窗口前置与遮挡校验、单 FIFO 上传队列、失败预算封顶 |
| 复用 | 框架 100% 可复刻；云端 OCR 不可复用；本地 RapidOCR 可替代但**不更快**（实测 0.5~0.8s/张） |

## 关键决策与理由

1. **不运行 exe、不联网**：只做静态分析，避免触发其鉴权与服务器交互，也避免合规风险。
2. **自研拆包工具而非用现成脚本**：`pyinstxtractor` 对 PyInstaller 6 的 88 字节 cookie 支持不稳，自己按 CArchive/PYZ 格式解析更可控（`_tools/` 下 4 个脚本，已复用性强）。
3. **用 `xdis` 而非 `dis`**：本机 Python 3.13 无法反汇编 3.11 字节码（名称表索引越界），`xdis` 跨版本可用。
4. **算法用"字节码还原 + 实测自比对"双验证**：还原出 `score_roi` 后，用素材自身当帧跑自比对，`hit=1.0` 与负例 `hit=0.42` 双向证实复刻正确。
5. **推翻自己的初始结论**：起初以为"本地 OCR 一定更快"，实测 830ms/张后如实修正报告与方案，没有为了叙事漂亮而保留错误数字。

| 坑 | 现象 | 解法 |
|---|---|---|
| PyInstaller cookie 长度 | 按 24 字节读不到 TOC | PyInstaller 6 是 88 字节（含 64 字节 `pylibname`），两种都探测 |

# 补充：联盟成员名单采集可行性验证

## 目标与结果

**目标**：验证「用同一套思路采集联盟成员昵称」是否可行（用户此前尝试准确率很低）。

**结果**：可行。样本 439×447（5 行，字高仅 10~13px）**5/5 全对，连跑 3 次一致**；439/878/1756 三种分辨率均 5/5。

## 核心结论：根因不在识别模型，在流程

| 原因 | 证据 | 影响 |
|---|---|---|
| **使用了带 det 的默认流程** | 同 ROI 只改高度，det 在 22~40px 区间整段返回空；关 det 后 1x~4x 全部 25/25 | 漏采，非读错 |
| 玩家自定义横幅污染 | 整图 OCR 出 31~36 条文本，仅 5 条是名字；横幅行与名字行同处 76.5px 格点、相位差 31px | 索引取值必错位 |
| 昵称长度差异大 | DORO(4) ~ PPORANGE(8)；左边界多收 20px → `DORO→3DORO` | 截断/带入 |
| 无格式校验 | 实测 `妮村的希望 1148114` 置信度 0.864 | 阈值拦不住 |

**关键数据**：det 全流程 1000~2600ms/行；rec-only 19~22ms/行。`use_det=False` **同时解决速度与准确率**（此前遗留待办第 3 条的预判被证实）。

## 三层解法（`04-复用方案/skeleton/alliance_ocr.py`）

1. 关 det 只跑 rec —— 行位置已知时无需检测
2. **格点拟合剔噪** —— 识别 y 坐标拟合等差数列，非格点丢弃（6 候选 → 5 正确，剔掉 y=389 的误报）
3. 昵称合法性校验 —— 长度 2~14、须含中日文/拉丁字母、含 4 位以上连续数字丢弃、命中 UI 词丢弃

## 标定参数（基准 439px 宽）

- 名字色 `#424242`，背景 `#F7F7F5`，行距 76.5px
- 名字带 x 比例 0.25~0.70（相对比例法，跨分辨率免重标定）
- ROI 上下各扩 40% 安全：实测上侵 18px、下侵 14px 仍全对

### 教训：.bat 必须纯 ASCII

首版 `启动.bat` 含中文且以 UTF-8 保存，cmd.exe 按 ANSI(GBK) 解码 → 整段乱码 → `'t' 不是内部或外部命令`，pythonw 压根没被调起，表现为「双击完全没反应」。

**规则**：
- `.bat` 文件内容不得出现任何非 ASCII 字节（含 `rem`/`echo` 里的中文），行尾必须 CRLF（cmd 定位 `goto` 标签依赖 CRLF）
- 主程序文件名也用 ASCII，避免 bat 引用中文路径
- 备一个 `调试启动.bat`（用 `python.exe` 前台 + `pause`），否则 pythonw 静默失败无从排查


## 关键决策与理由

1. **独立 venv（Python 3.12）**：本机 3.13 无 tkinter，3.14 太新。用 uv 的 3.12.13 建venv，装在项目内 `.venv`，不污染系统。
2. **tkinter 而非 PyQt/Electron**：零额外依赖，单文件可跑。
3. ~~**不自动滚动**~~ → **后来推翻了**，见下方「补充：自动滚采」。当时判断滚动距离不可控，实际用 `mouse_event` + 520ms 等待 + 跳行检测可以做到可靠。
4. **框选一次即可**：区域存 `输出/区域.json`。v2 起改存「占客户区的百分比」+ 窗口比例，窗口挪位/缩放都不用重框。
5. **负例也是交付物**：框宽了（含头像）无法自动修正，改为**明确报错**而不是默默出错。自测里专门断言这条。

# 补充：自动滚采（32 人一次采完）

## 目标与结果

**目标**：32 人一屏显示不下，需要"点一次→自己滚到底→全采完"，替代原来的人工滚动 + 反复点按钮。

**结果**：新增「自动滚采全部」按钮 + `滚轮 [N] 格/次` 调节。端到端实测 12 人 11.3 秒全采齐，零漏采零误采。

## 关键决策与理由

1. **滚轮用 `mouse_event` 而非 `PostMessage(WM_MOUSEWHEEL)`**：多数游戏只认真实输入队列里的滚轮，投递消息常被丢弃。实测本机 mouse_event 可用（Tk Listbox 一格滚 5 行）。
2. **滚动前必须 `SetForegroundWindow`**：用户是点工具按钮启动的，此刻工具在前台、游戏在后台，后台窗口多半不响应滚轮。所以第一次滚动前把目标窗口顶上来，停止时再把工具窗口拽回来并闪一下 topmost。
3. **跳行宁可停下报错，也不静默漏采**：两屏识别出的名字**完全不重合**即判定滚过头，立刻停止并提示调小格数。32 人的名单漏两个和报错，报错更有价值。
4. **默认 1 格**：不同游戏一格滚的行数不同（1~5 行）。1 格在 5 行/页的列表里必然有重叠，安全；调大只在一页 10 行以上才划算。
5. **用 `queue` 回传结果，不用 `threading` + `after`**：工作线程直接调 `self.after()` 会踩 `main thread is not in main loop`，关窗时还会在后台线程里炸一串异常。改成线程只往 `queue.Queue` 塞任务，主线程 `after(60)` 轮询执行。

## 踩过的坑

1. **Tk 渲染的字不能用来自测识别**：16 号字笔画只有 1px，`find_bands` 的纵向投影被打断，返回 0 个候选带。改 22 号加粗才够。这说明行投影对笔画粗细敏感——真实游戏 UI 笔画粗，所以不受影响。
2. **`geometry("+x+y")` 的坐标含标题栏**：直接拿它算截图区域会偏移 31px，末尾那行被切一半、识别成乱码。必须用 `winfo_rootx()/winfo_rooty()`（客户区原点）。
3. **`main thread is not in main loop`**：测试脚本用 `update()` 循环代替 `mainloop()` 时，子线程的 `after()` 必然报错。这既是测试驱动方式的问题，也暴露了产品代码的线程模型隐患，索性一起改成 queue。
4. **`except ... as e` 后的 lambda 闭包**：`e` 在 except 块结束时被释放，延迟执行的 `after(0, lambda: ...e...)` 会抛 `NameError`。必须提前绑定默认参数。

## 验证证据

```
e2etest.py（假游戏窗口，一页 5 行、共 12 人）
  滚轮实际响应 10 次 · 耗时 11.3s
  采到 12/12 人 → 全部采齐，无漏无误

e2etest.py 6（故意让一格滚 6 行）
  滚轮响应 1 次 · 耗时 2.7s
  ⚠ 两屏内容完全不重合，滚轮步长过大导致跳行 → 立刻停止
  采到 10/12（漏的正好是被跳过的那几行），但用户能看到明确警告
```

## 遗留待办（自动滚采）

1. 实机确认游戏里一格滚几行——若一格就跳过整页，1 格是下限，需要改键盘 ↓ 或拖动滚动条方案。

# 补充：窗口锁定（锁比例而非绝对坐标）

## 目标与结果

**目标**：用户提出「第一次锁定游戏窗口并验证比例与大小，第二次框选，然后开跑」。核心诉求是**安全**——宁可停下报错，不要静默采错。

**结果**：三步流程（① 锁定窗口 → ② 框选 → ③ 采集），采集区改存「占客户区的百分比 + 锁定时记录的宽高比」。`winlocktest.py` 22 项断言全过，覆盖挪窗口、缩放、比例变化、最小化、遮挡五个分支。

## 为什么这个改造是对的（原设计的真实隐患）

旧版 `区域.json` 只存屏幕绝对坐标。`_load_cfg` 无条件恢复并提示「窗口没变就不用重框」——但**程序自己无法判断有没有变**。

后果分两种：
- 一行都没识别出来 → 有告警，安全
- 碰巧截到带文字的区域 → **静默采进错误名字**，用户完全不知道

第二种才是必须修的。用户提出的"锁定比例"正好把它变成可校验的前置条件。

## 关键决策与理由

1. **锁的是客户区宽高比，不是分辨率**。比例一致但尺寸不同（16:9 全屏 ↔ 16:9 窗口化）允许继续跑，因为 NIKKE 的 UI 是等比缩放的，百分比坐标仍成立；比例变了（16:9 → 3:2）直接拒绝，因为画面会加黑边，UI 相对整个客户区的位置整体偏移，**自动适配只能靠猜偏移量**。
2. **hwnd 不能持久化**。游戏重启句柄必变，所以「锁定」是每次启动做一次的动作；盘里只存标题/尺寸/比例这类参考描述，有效性每次实时验证（`IsWindow` + `GetClientRect`）。
3. **每次截图前都走一遍 `resolve_region()`**，不只在采集开始时检查。窗口可能在两屏之间被挪走或最小化。
4. **比例一致时自动带出上次框选**。日常使用变成「点锁定 → 点自动滚采」，框选只在首次/换比例/UI 改版时做。这比用户原本描述的「每次都要框」省一步。
5. **遮挡检测按客户区中心点的窗口归属判**，并用 `GetWindowThreadProcessId` 把本工具自己的窗口从候选列表里排除——否则工具标题含 NIKKE，会混进候选或误判为遮挡者。
6. **v1 配置直接作废并备份**（`区域_旧版备份.json`），不做迁移：v1 没存窗口尺寸，反推不出比例，强行猜只会引入静默错误。

## 踩过的坑

| 坑 | 现象 | 解法 |

1. **联盟成员列表不响应鼠标滚轮**。画面差 1.3 是鼠标悬停的高亮动画，不是滚动。

2. 注入链路本身没问题（假窗口实测滚轮有效，画面差 10.45）。
3. 「画面差」根本不适合当滚动判据：会假阳（悬停动画）也会假阴（拖动不改像素差）。
   **改用名字序列对齐**：`match_rows(上一屏, 本屏)` 求最大重合前缀，

# 2026-10-27 16:45 拖动能采了，但 14 人就停：漏行判据自己把自己叫停

## 现象

诊断包 `诊断包_20261027_163156.zip`，`scroll_mode=drag`，采到 14 人停：

```
屏1 1-5 → 拖动 → 屏2 5-9（重合 1 行）→ 拖动 → 屏3 10-14（重合 0 行）
[W] 漏行：上一屏末尾 ['HGOLIVER','NING'] 在本屏全部消失
```

名单 1..14 **连续**，一个都没漏。旧判据 `_prev_tail`（"上一屏末尾两行消失 = 滚过头"）
在"恰好换一整屏"时必然触发，而 32 人 / 每屏 5 行时正常采集几乎每一步都是这个形态。

## 数学结论（这条要记住）

- 漏人 ⟺ **滚过行数 > 本屏行数**。旧判据用的是 `≥`，所以必然误报。
- 但两屏零重合时，名字序列只能量到"至少一屏"：`match_rows` 恒返回 `len(上屏)`，
  "刚好一屏"与"跳过 3 行"数据上完全同形。**光靠名字无法区分，不要试图靠放宽阈值解决。**
- 正确解法是让零重合别发生：**闭环控制步长，使每次只走 2 行**（每屏 5 行时恒留 3 行重合）。
  一旦仍然发生，就停、降步长、把话说清楚（"可能没漏也可能漏，分不出来"），不要假装知道。

## 改动

- `judge_roll(prev_ordered, cur_ordered) -> (rows, overlap, verdict, note)`，verdict ∈ none/ok/jump/stuck
- `plan_drag(pitch, fling, clicks) -> px`：`TARGET_ROWS(2) × 行距 ÷ 惯性倍率`，clamp `[40, 420]`
- 行距 = 每屏昵称 y 的中位差；惯性倍率 = `行数 × 行距 ÷ 上次拖动距离`，EMA α=0.5
- 零重合（jump）时 `fling *= 1.8`，步长自压到 ~40px
- 删除 `_prev_tail`

## 踩的坑

1. **拖动不能用 Tk 事件模拟**：`drag_at()` 在 Tk 主线程 sleep + `SetCursorPos`，主循环阻塞，
   `<B1-Motion>` 全部堆积到拖动结束后才派发；且按下/抬起都落在终点坐标上。
   → e2etest 改成独立线程轮询 `GetAsyncKeyState(0x01)` + `GetCursorPos` 累计位移，等效跨进程。
2. e2etest 的假窗口是主程序的 Toplevel，同进程抢前台，拖动后立刻误报"丢前台焦点"。
   → 测试里 `tool.is_foreground` 打桩，前台归属交给 `winlocktest` 覆盖（别在 e2e 里重复验证）。

# 2026-10-28 00:20 导航点完联盟却没点队员：跳过判据漏了 need 非空校验

## 现象

第一轮实战。工具正确点了主页右侧「联盟」，进入联盟概览页，然后**直接收工**，
没点顶部「队员」。日志两行：

```
[nav] 第 2/2 步 · 判定在「联盟概览」（指纹 5 词）
[nav] 已经过了「联盟概览」这一关，跳过
[nav] 导航走完，但试拍只认出 1 行
```

日志本身毫无破绽——页面确实在联盟概览，跳过也确实有理由。这是这类 bug 最毒的地方。

## 根因

`_nav_run` 里"这一步过没过"的判据丢了 `step.need` 非空校验：

```python
# 错
if need_ok(texts, step.need):
```

而 `need_ok(texts, None)` 按设计**返回 True**（"没有要求 = 已经满足"）。最后一步
（联盟概览 → 成员页）本来就没有"点完该到哪一页"，于是被恒定判成"已经过了"，永远跳过。

上一轮重构时把这行从 `if step.need and hit_words(...)` 改成了 `if need_ok(...)`，
把 `step.need and` 一起丢了 —— 自己引入的回归，且 navtest 当时只测纯函数 `need_ok`，
没测"哪一步该跳"这层控制流，所以 48 项全绿也没拦住。

## 改动（`engine/alliance_ocr.py`）

抽出纯函数，把"该不该跳"变成可断言的东西：

```python
def nav_skip_step(step, texts) -> bool:
    return bool(step.need) and need_ok(texts, step.need)
```

主循环改用它。navtest 新增第 8 组 6 项，其中两条是核心：

- 站在联盟页时，最后一步（→队员）**不许**跳过
- `need_ok(texts, None) is True`（证明这道挡板不能省，省了就是 bug）

## 教训

**凡是"跳过某一步"的分支，都必须有断言证明"该跳的时候才跳"。**
只测被调用的纯函数不够——函数本身没错，错的是调用处少了个前置条件。

# 2026-10-28 02:15 滚采"猛地下滑到底部 + 每轮漏一半"：三个参数 + 一个不该动的光标

## 现象

真机连跑三轮，人数是 `[33, 32, 12]`、`[19, 6, 11]`、`[6, 6, 11]` 这种量级，同一份代码
同一份数据，轮次之间差十个人。用户的原话：**"还是会突然猛的下滑到底部，而且每次都会漏"**。

## 根因（三条，互相独立）

### 1. 起手死区没算进去 → 步长永远差小半行

拖动前十几像素被游戏当成"区分点击还是拖动"吃掉，不产生滚动。实测：

| 拖动距离 | 内容实际位移 | 死区 |
|---|---|---|
| 60px | 42px | 18px |
| 70px | 57px | 13px |
| 89px | 71px | 18px（正好一个行距） |

旧代码步长 = 行距 = 71px → 真实位移 **0.80 行**。每一步都差一点，相位一路往后漂，
漂到某一步就跨不过行边界——名字一个不变。而旧逻辑把"名字不变"直接当成"地址到底了"，
于是 32 人的联盟**只采到 6 个人**就报"✅ 已到列表末尾"。

修：`plan_drag()` 加回 `DRAG_SLOP`，目标 1.25 行 + 死区 ≈ 104px；并且"走 0 行"不再直接
判定到底，先**把步长放大一倍重试一次**（真到底放大也推不动，卡在两行中间一步就跨过去）。

### 2. 拖动速度 250px/s 会甩屏

同一距离换速度连拖对比：250px/s 时每 5~10 步甩一次，惯性把列表滑掉整屏（两屏零重合）；
107px/s 连续 28 步零跳步。改为 `DRAG_STEP_PX=3 / DRAG_STEP_GAP=0.028`。

### 3. 松手后立刻挪光标 = 540px 的甩动 ← 真凶

拖动松手后程序要马上把光标从拖动终点 `(604,631)` 请到角落 `(63,184)`，横向 540px。
游戏处理 `LEFTUP` 晚一两帧，这段时间仍认为手指按着，于是这 540px 被当成一次大甩动，
**列表一路甩到最底部**。

识别它的关键是落点：不管从第 4 行、第 5 行还是第 12 行开始跳，落点永远一模一样，
而且正好是名单**最后 5 行**。只有一个绝对位置才会这样——不可能是距离算错。

修：`LEFTUP` 之后先停 `RELEASE_SETTLE=0.18s`，谁都别动光标。

## 附带：跳步不再作废整轮

即使偶尔还是跳一步，也先**往回走小步补采**：一路认名字，直到和"跳步前那一屏"重合
就继续往前。补采那几步**一个名字都不记**——否则会把 OCR 歪读法（命OVO→命OVo/命oVo）
当成新成员灌进库，实测一轮多出三个人。

## 附带：别名不许从"只露一次"的路径学

`_roster_apply` 的收工对账原先会把 `(读歪的写法, 归到的写法)` 记成永久别名。但那条路径
的证据只有"字面像 + 本趟只露过一次"，**方向可能是反的**：实测库里有「命OVO」，某轮读成
「命OVo」正好只露一次，于是学成"命OVo 才是正名"，之后每轮跟着错，名单凭空多一人。
别名现在只由 `_merge_misreads` 记——那里靠"相邻两屏同一物理行"投票，能定方向
（实测 4 屏 vs 1 屏）。昵称库里的 `命OVo` 已清理（备份 `预设/昵称库_备份_20261028_0210.json`）。

## 诊断工具（都是真机跑的）

| 工具 | 干什么 |
|---|---|

# 2026-10-30 14:00 采多了就裁，别在"像不像"上继续调参 + 打包成单文件 exe

## 起因

上一轮真机是 `34 / 32 / 32`，第一轮多 2 人，但每轮都 `complete=True`。
**"看着对"比"报错"危险**：一旦接上退会判定，多出来那两人会一直躺在名单里，
每轮都被算成"新成员"。

## 取证：两个多出来的名字，成因完全不同

从 `输出/操作日志.txt` 里 `scan:` 行捞出来，对照真名：

| 多出来的 | 真名 | 出现屏数 | 为什么躲过位置合并 |
|---|---|---|---|
| 腊目夜 | 朧月夜 | 1 / 24 | 相似度 0.667 够、位置也对，但落在那一屏的**最后一行**，下一屏已滚出去，位置证据没有第二次机会 |
| 入魔工 | 大魔王 | 1 / 24 | 四个字读成三个完全不同的字，相似度 **0.33**，比 `same_row` 的 0.5 门槛还低 |

（顺带纠正上一轮自己的一个误判：`_merge_misreads` 的 `ordered[:overlap]` 范围**没有算错**，
和 `judge_roll` 的位移量是自洽的，本屏最后一行本来就没有上一屏位置可对。）

## 放弃的方案：放宽 same_row

第一反应是把"必须等长"改成"长度差 ≤1"。放弃了：

- 救不了「入魔工」——三个字全错，长度一样也没用；
- 会把「空木/空本」「萧白/英白」这些本来就贴着 0.5 门槛的配对推过线。

**放宽门槛换来的不是准确率，是误并真人的风险。**

## 实际方案：`_trim_to_total(total)`

页面上那个 `(32/32)` 是**唯一不依赖识别质量的硬事实**。不管位置对齐有没有盲区、
字面相似度够不够，联盟里就是 32 个人。判据换成：

> 真成员每屏都在，误读只闪一两次。整趟 24 屏里平均每人 3~4 屏，误读全是 1 屏。

从"屏数最少"往下丢，直到和页面人数相符。三道保护：

| 保护 | 阈值 | 防什么 |
|---|---|---|
| 只从"屏数 ≤ 1"里挑 | — | 真成员至少 2 屏，是下限不是统计猜测 |
| 单轮最多裁 5 个 | `MAX_TRIM` | 超出说明是别的问题（总数本身读歪了） |
| 页面人数在 3~200 | `TRIM_TOTAL_RANGE` | 那个数字也是 OCR 读的，会歪成 1 或 999 |

可裁的不够时**宁缺毋滥**，剩下原样留着并告警"请人工核"，绝不拿屏数 2 的真成员凑数。

**调用位置很关键**：必须在 `_commit_roster()` 之前。只告警不够——实测那两个名字

1. **永远停在最新一行**：每批写完 `see("end")`，并把末行打上 `LAST` 淡底——

## 为什么不是"给昵称库表加一列"

昵称库是**一个人一行**（`first`/`last`/`rounds`/`miss`），能回答"现在少了谁"，
回答不了"**哪一轮**少的"：

- `miss=1`、`last` 是昨天 → 可能是漏采，也可能真走了，看时间分不出
- 换成"第 81 轮还在、第 82 轮没了" → 能对着那一轮的画面回想

所以要的是**每轮一行**的留档，而不是给现有记录加字段。

## 落档在 `_commit_roster`

```json
{"t": "...", "n": 32, "total": 32, "ok": true,
 "add": [...], "gone": [...], "drop": [...], "alias": 1}
```

- `ok` = 完整采到末尾；**只有 true 的轮次参与退会判定**（`gone` 早就被这个条件守着，
  这次把 `add` 的可信度也在视图里说清楚）
- `add` 首轮建库故意留空（整张名单都是新增，报了没意义）
- `drop` 是这轮达到 `ROSTER_DROP=2` 被移出的
- 上限 `ROSTER_HISTORY_MAX=24`，存时间序、看倒序

## 视图 `churn_dialog`

顶部一句话（最近一轮/采到几人/页面几人/累计几轮）→ 轮次表（未采完整行压暗、移出标红）
→ 选中那轮的详情（新来的/没见到/已移出/误读归位）→ 当前连续没见到的人。

只提示不动作的两条：**1 进 1 出 → "可能是改名"**（真"走一个来一个"时自动合并会把两人记录搅在一起）；
**`ok=false` 的轮次连"新增"都不可信**（漏采导致的重认会被当成新人）。

## 把判据抽成纯函数，是因为错了看不出来

`roster_history()` / `churn_headline()` 不碰界面。把"没来的人"误判成"退会"，
界面上只是显示"移出 1 人"，看着完全正常——所以只能靠单测盯。`churntest.py` 55 项里
30 项围着这两个函数（未采完不记未见、连续两轮才移出、首轮不刷新增、上限裁剪、

1. **移出库不进摘要**：`names.pop()` 之后只写一行 WARN，收工那句"本轮 32 人·库内 32 人"
   看不出有人被移出。移出不可逆（下次进来算新人），已在摘要里点名。
2. **`roottest` 的 Fake 缺 `_total_hint`**：补字段，而不是在代码里写 `getattr(..., 0)`

### 22:35 补滚采链路：三屏联测抓出一个真 bug

# 2026-11-07 11:00 桌面启动 bat + 一个只有 pythonw 才炸的坑

## 桌面 bat

`C:\Users\1E_6\Desktop\NIKKE困难采集.bat`，由 `D:\Codex\临时\gen_desktop_bat.py` 生成。
三个必须记住的点：

| 点 | 原因 |
|---|---|
| **必须按 GBK 写盘** | cmd 按 GBK 解析 .bat，而工程路径含中文「OCR采集」。写成 UTF-8 会让 `cd` 整行变乱码 |
| **必须带自提权** | 游戏以管理员运行时，普通权限进程的鼠标注入被 UIPI 拦掉（能截图能识别、就是拖不动） |
| 不写 BOM | 带 BOM 的 bat 第一行会变成 `\ufeff@echo off`，cmd 报「不是内部或外部命令」 |

实测：`cd` 到中文路径返回 `CD_OK`、`VENV_OK`；PowerShell 能正确解析中文 bat 路径
（`Test-Path -LiteralPath` 返回 FOUND），所以自提权那段可用。

## 坑：pythonw 下 `main()` 漏了 `_fix_streams()`，窗口根本不出来

`hard_client.main()` 原来只调了 `dpi_aware()`。而 **pythonw.exe 下 `sys.stdout/stderr` 是 None**，
RapidOCR 启动时会往 stderr 打一行 `[INFO] Using engine_name...`，于是进程静默退出——
连窗口都不创建，任务管理器里只看到 pythonw 停在那里吃 100MB 内存。

`alliance_ocr._fix_streams()` 就是干这个的（把 stdout/stderr 接到日志文件），补上一行即可。
验证：改前枚举不到窗口；改后立刻出现「联盟突袭 · 困难模式采集（demo）」。

**教训**：任何用 pythonw 启动的入口，第一件事必须是 `_fix_streams()`，不是 `dpi_aware()`。


### 2026-11-07 11:20 拖动「明明动了却报 0px」——两个测量缺陷

真机连续三轮卡在「拖动试探 位移 0px → 三种都推不动 → 中止」，用户肉眼确认画面确实在动。
取证脚本 `D:/Codex/临时/probe_shift.py`：用困难样张 + 真机框选比例合成「只有列表区域移动」的两帧。

| 测法 | 框内内容移动 240px 时量到 |
|---|---|
| 整屏 `measure_vshift` | **0px**（相关 0.63） |
| 框内 `measure_vshift` | 240px（相关 0.94） |
| 反向（内容下移）`measure_vshift` | **0px**（只搜 `s>=0`，负半轴取不到） |

1. **测的区域不对**：`measure_vshift` 把每行压成笔迹强度标量做相关；整屏里标题栏、日期 tab、
   左右面板、底部按钮全是静止的且占多数，最优位移永远落 0。采集主循环一直用 `box` 裁内测，
   所以偶尔能跑；`_calibrate_drag` 和 `_scroll_to_top` 用整屏 → 永远 0。
2. **只能测正位移**：拉回顶部是「内容下移」，需要负位移 → 永远 0，与「没动」同形。
   这就是「故意划到底后拉不回顶部」的根因。

修法：`alliance_ocr.measure_vshift_signed()`（旧函数不动，只往下滚的调用方不受影响）＋
`hard_client._measure()` 统一「裁框内 + 带方向」；`_scroll_to_top` 判据改 `abs(shift)`；
`_calibrate_drag` 改为**取三种候选的最大位移**，并加两条兜底：
松手后立刻再拍一帧与停稳帧取较大者（防弹窗回弹抹平位移）、像素全失败时用 `_content_moves()` 比内容。

**教训**：量位移必须(a)只量会动的区域、(b)支持两个方向；否则「0」同时代表"没动"和"量不到"，
而这两种情况的后续处理完全相反。
