## 1. 第一原则：放弃通用，换零配置

工具只服务**胜利女神：新的希望 PC 客户端**这一家。这句话省掉的复杂度很可观：

| 通用工具要做的 | 只服务一家时不用做 | 省下的收益 |
|---|---|---|
| 任意窗口识别、任意分辨率 | 只认一个进程 + 一个标题 | 接窗稳定性↑，误接概率→0 |
| 任意 UI 布局标定 | 内置预设 + 比例换算 | 首次使用零配置 |
| 用户自选识别区域 | 区域固化进预设 | 没有"框错了"这类支持成本 |
| 兼容多种比例 | 只保证 16:9，其余明确拒绝 | 坐标永远对得上 |

**可以进一步推进到"内置一份 16:9 黄金预设当唯一真值"**：只要有效画面是 16:9，百分比坐标就恒定成立，标定这件事可以从"用户做一次"变成"出厂就有"。

### P1 · 导航自动化（已完成，只覆盖"主页 → 成员页"这一段）

目标：不管停在哪个界面，一键到「联盟成员」第一行；采完一键退出列表。

**状态**：主页 → 联盟概览 → 成员列表 这条主路已落地并跑通真实截图回放
（`navtest.py` 55 项）。"采完一键退出列表"还没做——那需要先知道退出后该回哪里。

**实战第一轮就踩了个自伤**：点了「联盟」进到联盟页，然后**没点「队员」**，日志写着
「已经过了『联盟概览』这一关，跳过」。根因是跳过判据漏了 `step.need` 非空校验——
`need_ok(texts, None)` 按设计返回 True，而最后一步（→队员）本来就没有"点完该到哪"，
于是被恒定判成"已经过了"。已抽成纯函数 `nav_skip_step()` 并加了 6 条断言钉住
（`navtest.py` 第 8 组）。

教训：这类 bug 的杀伤力在于**日志读起来完全合理**。以后凡是"某一步被跳过"的分支，
都要有断言证明"该跳的时候才跳"。

同期补了独立小工具 `clickprobe.py`：锚点算错时不用再靠猜，直接在游戏里点，
它把坐标、点前/点后画面、识图结果和偏差一起出报告。后面加会战页锚点会反复用到。

**技术选型：OCR 关键词指纹 + 比例坐标点击。**

不用像素模板匹配，理由是版本更新改一个图标就全废，而按钮**文字**几乎不会变。每个页面只定义两样东西：

```python
NAV_SPEC = (
    NavStep("home", "主页",
            probe=("方舟", "大厅", "物品栏", "队员招募", "作战出击", "MISSION PASS"),
            target="联盟",
            area=(0.935, 0.230, 1.000, 0.560),     # 右侧竖排图标
            preset=(0.970, 0.418)),
    NavStep("guild", "联盟概览",
            probe=("日志", "联盟公告", "联盟功能", "联盟射击场", "联盟商店", "退出"),
            target="队员",
            area=(0.440, 0.230, 0.560, 0.330),     # 顶部标签条里「队员」那一格
            preset=(0.500, 0.278)),
)
```

**实测踩到的三件事，都写进代码注释了**：

1. `主菜单` 会被 OCR 读成 `主选单`（差一个字，`in` 判不中）→ 指纹里不写它
2. `商店` 在联盟页也会命中（`联盟商店`）→ 主页指纹不含"商店"，避免两页搅在一起
3. 白名单上界必须压到 `y ≥ 0.23`：再往上就把顶端「钻石 1552210」圈进来了。
   这个数字条本身不是付费按钮，但它是个入口，能点就不该放进白名单

每步固定动作：

```
截图 → 判定当前页（指纹命中 ≥2 个关键词）→ 命中则点该页的 enter 坐标
     → 未命中 → 报"现在停在哪一页"并中止（绝不盲点）
     → 点完等 0.6s 再判下一页，最多重试 3 次
```

**四条铁律**（每条都针对一个真实的踩坑方式）：

1. **绝不盲点**：坐标只在"当前页指纹校验通过"后才生效。页面判不出来就停，宁可不做。
2. **不点非常规按钮**：只允许 `PAGES` 里登记的坐标。抽卡、充值、邮件领取这类一律不在白名单内。
3. **先清弹窗**：进入前扫一遍屏幕中央 60% 区域，命中"关闭/确认/公告"这类词就先点关闭，最多清 3 层。
4. **可回退**：任一步失败按 `ESC` 一次退到上级，再重新判页，不连续乱按。

**还需要你提供的**：成员页本身的截图（1 张）。现在终点的判定是"昵称列能扫出 ≥3 行"，
够用但不精确——如果成员页顶部有「联盟成员 32/32」这类计数或者「申请」页签，
就能像前两页一样配指纹，导航结束时的报告也能直接说出人数对不对。

### P2 · 会战伤害统计

**先定数据模型，等玩法开了只补样本、不用重构：**

```python
@dataclass
class GuildRaidRow:
    member: str        # 昵称 —— 直接复用昵称库，识别率直接继承
    damage: int        # 纯数字，去掉千分位和单位
    rank: int | None   # 排名列（如果有）
    team: int | None   # 第几队 / 第几刀（如果有）
```

采法跟成员页是同一套：**行切分 → 每行再按列切开 → 名字列走 OCR → 数字列走 OCR + 数字专用后处理**。复用点：

| 模块 | 复用 | 差异 |
|---|---|---|
| `find_bands` 行切分 | 直接复用 | 行高不同，参数可配 |
| `scan` 列切分 | 复用结构 | 多一个数字列，颜色掩码不同 |
| 昵称库 | **完全复用** | 会战页的人就是联盟成员，库里全有 |
| 滚动采集 | 直接复用 | 会战列表通常一页显示完，可能不需要滚 |

**坑都在数字上**，现在就能写解析器并单测：

- 千分位分隔符（`1,234,567` / `1234567` / `1 234 567`）
- 单位后缀（`K` / `M` / `万` / `亿`，以及中文版可能的`万`）
- 右对齐导致数字和名字粘连（`DORO1,234,567`）
- 颜色编码（不同伤害档位颜色不同，颜色本身是可用信号）

现在可交付：`parse_damage()` + 20 组合成样本单测。等玩法开了只需补真实截图调阈值。

### P3 · 客户端封装

`ArcanaHelper-V1.1.1.exe` 是 **PyInstaller 单文件**（97.5 MB，内含 `pyi-` 引导段）。我们这个工具同栈（Python + tkinter），走同一条路最省事。

**打包清单（每一项都踩过或必踩）：**

| 项 | 做法 | 不做的后果 |
|---|---|---|
| 数据目录 | `APP_DIR` 用 `sys.executable` 的父目录（已修） | 昵称库/导出写到临时目录，重启全丢 |
| OCR 模型 | `--add-data` 打包 `rapidocr/models/*.onnx` | 首次启动联网下载，离线机直接不可用 |
| 管理员权限 | manifest `requireAdministrator` | 游戏管理员运行时截不到图、发不进滚动 |
| 图标/版本 | `--icon`、`--version-file` | 右键属性一片空白，像可疑程序 |
| 控制台 | `--windowed`（`pythonw` 语义） | 多一个黑框 |
| 单文件 vs 目录 | 单文件启动 3~8 秒解包；`--onedir` 秒开但要发文件夹 | 用户以为卡死 |

**建议先出 `--onedir` 内部版**（改一行代码热替换即可，调试快），稳了再出单文件对外版。

**杀软误报**是 PyInstaller 的老毛病，对策优先级：代码签名 > 提供 onedir 版 > 提交误报申诉。别指望"加个 UPX 壳"能解决，那反而更容易被拦。

## 2.5 滚动稳定性：三个数决定一切（真机实测收敛）

"一步走一行"这句话由三个数决定，每一个都得实测，猜错任何一个就是"猛地下滑到底部"
或者"每轮只采到一半"。

| 参数 | 实测值 | 猜错的后果 |
|---|---|---|
| 起手死区 `DRAG_SLOP` | 13~18px（拖 70px 只挪 57px） | 步长按行距给 → 真实只走 0.80 行 → 相位漂到某步跨不过行边界 → 名字不变 → **误判"到底了"，32 人只采到 6 人** |
| 拖动速度 `DRAG_STEP_GAP` | ≈107px/s（3px / 28ms） | 250px/s 时每 5~10 步甩一次，惯性滑掉整屏 → 两屏零重合 → 中间的人全丢 |
| 松手静止窗 `RELEASE_SETTLE` | 0.18s | **真凶**：松手后立刻把光标从拖动终点瞬移到角落（540px），游戏还没处理完 LEFTUP，把这 540px 当甩动 → 列表一路甩到最底部 |

第三条是靠"落点永远是同一个绝对位置"认出来的：不管从第 4 行、第 5 行还是第 12 行开始跳，
落点都是名单**最后 5 行**。只有一个绝对位置才会这样，不可能是距离算错。

配套加了两道保险：

- **"走 0 行"不再直接判定到底**：先把步长放大一倍再试一次。真到底放大也推不动，卡在两行中间一步就跨过去。
- **跳步不再直接作废整轮**：先往回走小步，把跨过去的人重新读一遍再继续（补采那几步**一个名字都不记**，否则会把 OCR 歪读法灌进库）。

真机验证：**连跑 4 轮，每轮 24 次滚动、32 人（游戏内显示 32/32）、零跳步、轮轮一致。**

诊断工具链（都是真机上跑的，不是单测）：`实测滚采.py`（多轮对比人数）、`拖动标定.py`
（距离 → 行数 → 真实位移，拟合死区）、`速度实验.py`（换速度统计跳步）、
`逐帧.py`（把每步 scan 原始输出和 ROI 原图都存下来）。

**这一轮最大的教训是"别信单一证据"**：中间两次被自相矛盾的数据带偏——一次是
`judge_roll` 两个参数写反，报出"走了 5 行、零重合"；一次是只看名字推位移，把
"1.0 行"和"1.35 行"当成一回事。**名字序列和像素位移必须一起看，两者打架就说明结论有问题。**

## 3. 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 客户端改版动了导航按钮文字 | 导航断在某一页 | 每页 `must` 关键词配 3 个以上冗余，命中 2 个即认 |
| 反作弊把模拟点击当异常 | 封号风险 | **只用 Windows 标准输入消息**，不注入、不读内存、不改客户端文件；节奏加随机抖动 |
| 游戏内分辨率/缩放被玩家改过 | 坐标偏移 | 比例硬校验已在，非 16:9 直接拒绝并说清 |
| 会战页面配色与成员页差异大 | 颜色掩码失效 | 颜色阈值做成角色配置，不写死 |
| 单文件 exe 被拦 | 用户装不上 | 签名 + onedir 备选 |

关于反作弊这条要说明白：**只做屏幕像素 + 标准输入**，不碰进程内存、不注入 DLL、不修改客户端文件——这是"读屏工具"和"外挂"的分界线，也是这条线不能越的地方。

## 9. 2026-10-30：竖版界面 + 流程可视化 + 同步预留

### 目标

用户原话：**"根据阿卡客户端的设计理念优化采集器：界面竖版、操作流程可视化、
技术实现全面看齐 ArcanaHelper、预留同步接口"**。

### 从 ArcanaHelper 身上学的四件事

设计基线不是猜的，是从 `%APPDATA%\ArcanaHelper` 里反推出来的：`config.json` 存
`selectedCharacters + key`；`log/*.log` 能看到它的全部骨架；窗口是 616×839 的竖条。

| 它怎么做 | 我们怎么落地 |
|---|---|
| `Recognizer.classify` 逐页打分（命中率/误差/原因），连续 N/2 才采信 | `classify_scene()` + `_confirm_scene()`，日志同款格式 |
| 每次运行一个 `<时间戳>/temp` 目录 | `_run_temp()`：`输出/2026-10-30_12-32-16_211/temp` |
| 失败落 ROI 图 + 双坐标（client_roi / screen_roi / client_size） | `_failure_roi()`，导航判不准和框选异常时各落一帧 |
| 待上传队列（endpoint + 用途 + 文件），先落盘再上传 | `sync_client.py` 的 Outbox，`待上传 endpoint=… 用途=… 文件=…` 同款日志 |
| 请求失败诊断 JSON | `{status, error_type, reason, endpoint, method, attempts}` |

### 没照抄的两处

1. **它用颜色命中率判页，我们仍用文字指纹。** 颜色阈值对环境光、主题皮肤敏感，
   我们手上已有稳定的 OCR 指纹（navtest 55 项钉着），换成颜色是降级。
2. **它的"任务提示"写两遍**（一次带 `running N%`、一次不带）。那是它把 GUI 状态栏和
   日志分开维护留下的重复，我们合成了一行。

### 踩的坑

**`pack(side="bottom")` 是"后放的在上"。** 两排工具行按视觉顺序写，结果上下颠倒，
而且看起来"就是这么设计的"——不截图根本发现不了。以后凡是 `side="bottom"` 叠多层，
**创建顺序必须和视觉顺序相反**。

**`tk.Frame(padx=…, pady=(2, 8))` 会抛 `bad screen distance "2 8"`。** 只有 `pack()`
的 padx/pady 接受二元组，Frame 自己的构造参数不接受。同理 `ttk` 的 `heading` 底色
在 `clam` 主题下要连 `map()` 一起配，否则 active 状态会盖掉 `configure()`。

**PrintWindow 会把 ttk 控件抓成未重绘的旧缓存。** 截图核排版时表头永远是浅色，
换成屏幕复制才看到真实样子。**截图工具的偏差会伪装成产品缺陷。**

## 10. 2026-10-30：把「每轮人数都对」钉死 + 打包成单文件 exe

### 起因

上一轮结束后，真机数据是 `34 / 32 / 32`——第一轮多 2 人。数字看着不大，但每次
`complete=True`。**"看着对"比"报错"危险**：一旦接上退会判定，多出来那两个人会
一直躺在名单里，每轮都被算成"新成员"。

### 三个名字的实测取证

从日志里把那两个多出来的名字捞出来，逐个对照真名：

| 多出来的 | 真名 | 出现屏数 | 为什么躲过了位置合并 |
|---|---|---|---|
| 腊目夜 | 朧月夜 | 1 / 24 | 相似度 0.667 够、位置也对，但它落在那一屏的**最后一行**——下一屏已经滚出去，位置证据没有第二次机会 |
| 入魔工 | 大魔王 | 1 / 24 | 四个字读成三个完全不同的字，相似度只有 **0.33**，比 `same_row` 的 0.5 门槛还低 |

第一反应是去放宽 `same_row`（把"必须等长"改成"长度差 ≤1"）。**放弃了**：它救不了
「入魔工」（三个字全错，长度一样也没用），却会把「空木/空本」「萧白/英白」这些
本来就贴着 0.5 门槛的配对推过线——放宽门槛换来的不是准确率，是误并真人的风险。

### 换了个方向：用页面人数当硬约束

页面上那个 `(32/32)` 是**唯一不依赖识别质量的硬事实**。不管位置对齐有没有盲区、
字面相似度够不够，联盟里就是 32 个人。所以不再纠结"哪两个是误读"，而是：

> 真成员每屏都在，误读只闪一两次。整趟 24 屏里平均每人 3~4 屏，误读全是 1 屏。

从"屏数最少"往下丢，直到和页面人数相符。这个判据不看字面、不看位置，正好补上
那两套判据共同的漏洞。

三道保护（少一道就会删真人）：

| 保护 | 阈值 | 防什么 |
|---|---|---|
| 只从"屏数 ≤ 1"里挑 | — | 真成员至少 2 屏，这是下限不是统计猜测 |
| 单轮最多裁 5 个 | `MAX_TRIM` | 超出说明是别的问题（比如总数本身读歪了） |
| 页面人数在 3~200 | `TRIM_TOTAL_RANGE` | 那个数字也是 OCR 读出来的，会歪成 `1` 或 `999` |

可裁的不够时**宁缺毋滥**：只裁能裁的，剩下原样留着并告警"请人工核"——绝不拿
屏数 2 的真成员凑数。

关键细节：裁剪必须在 `_commit_roster()` **之前**。只告警是不够的——实测
「腊目夜」「入魔工」各在昵称库里活了两轮才被移出，期间每一轮都在教库"这两个是成员"。

### 打包

`打包.py` 一条命令：清 dist → PyInstaller → 附带使用说明。115MB 单文件，
内置 RapidOCR 三份 onnx 模型 + 标定预设，双击即用。

两个必须处理的坑：

1. **模型是运行时按文件名拼路径读的**，静态分析发现不了。不加
   `collect_data_files("rapidocr")` 的话，exe 一启动就去网上下模型，没网直接崩。
2. **`_app_dir()` 冻结态返回 exe 目录**，所以随包带的预设全留在 `_MEIPASS` 那个
   每次启动都重建的临时目录里——不搬出来，exe 永远认不到内置标定。加了
   `_seed_presets()` 首次启动播种，只补缺失、不覆盖。

## 11. 2026-10-30：运行日志要能"边跑边看"

用户提得很具体：**采集成员的时候要参考运行日志，实时滚动到最新条目。**

先量了一下现场，问题不在"滚不滚"，在"滚得动但读不了"：一轮滚采每步写 8 行、
1.6 秒一步，也就是 **≈5 行/秒**——5 行高的框子 1.2 秒就换一遍版面，等于没法看。

### 三件事一起改

| 要求 | 做法 | 验证 |
|---|---|---|
| 新行一进来就在最下面 | 每批写完 `see("end")`；末行加淡底，眼睛直接落在最新那条 | uitest「写满后停在最新一行」 |
| 别只有 5 行 | 开跑 `_log_mode(True)` 撑到 9 行，收工收回；右侧 `⇕` 可拖，拖过就固化 | uitest「开跑会展开并撑高 / 用户拖过的高度不再被自动改」 |
| 翻历史别被拽回来 | 滚轮/滚条/翻页键一有动作就暂停跟随，标题变蓝 + 右下角 `↓ N 条新`；回到底部或点角标自动恢复 | uitest 4 项（含"首行行号前后一致"） |

### 写入改成队列（这条是修 bug，不是加特性）

日志是采集线程写的，原先直接 `logpane.append` —— 在子线程里碰 Tk 会偶发抛
`main thread is not in main loop`，而 `log()` 外层有 `except: pass`，结果就是
**静默丢行**，偏偏缺的常是最关键那条。改成 `push()` 只入队，主线程 80ms 抽一批、
批量入库后统一滚动。压测：子线程连写 200 条，一条不丢（uitest 第 8 组）。

### 一个必须记下来的 Tk 坑

`Text` 在 `state="disabled"` 下，连**程序化**的 `delete` 都会被静默忽略——不报错，
也不删。第一版把 `configure(state="disabled")` 放在裁剪之前，400 行上限形同虚设
（实测涨到 426 行）。裁剪和打标必须排到恢复只读之前。

### 顺带修掉的

- 日志 `wrap` 从 `none` 改成 `char`：窄窗里长行原本被右边缘截断，读不全。
- 跟随状态的判据只认**用户输入**，不认 yview 数值变化——否则改窗口高度、日志裁剪
  引起的抖动都会被误判成"用户在看历史"，标题一直挂着"已停在历史"。

## 12. 2026-10-30：退会判定看得见（成员变动视图）

上一轮收尾时把待办摊开成 A~D，A（识别层收尾）和 D（打包）做完了，剩下 B：**退会判定视图**。
数据层其实早就齐了（`rounds` / `miss` / `alias`），差的只是"把话说出来"。

### 先说为什么不能直接拿库里的字段画个表

昵称库记录的是**一个人一行**：`first` / `last` / `rounds` / `miss`。它能回答"现在库里少了谁"，
回答不了"**哪一轮**少的"。而这两件事对判断的影响完全不同：

- `miss=1` 且 `last` 是昨天 → 可能是漏采，也可能人真走了，看时间看不出来
- 同一件事换成"第 81 轮还有人、第 82 轮没了" → 立刻能对着那一轮的画面回想

所以加的是**每轮一行**的留档，而不是给昵称库加字段。

### 落档（`_commit_roster`）

```json
{"t": "2026-10-30 14:18", "n": 32, "total": 32, "ok": true,
 "add": ["冷面笑匠"], "gone": ["灰姑娘"], "drop": [], "alias": 1}
```

| 字段 | 含义 | 注意 |
|---|---|---|
| `ok` | 这轮是不是完整采到列表末尾 | **只有 true 的轮次参与退会判定** |
| `add` | 库里之前没有的名字 | 首轮建库时故意留空——整张名单都是"新增"报了没意义 |
| `gone` | 这次没见到、但还没到移出条件 | 未采完的轮次一律不写 |
| `drop` | 这轮达到 `ROSTER_DROP=2` 被移出库 | 顺带修掉一个洞：以前只留一行 WARN，收工摘要里看不到 |
| `alias` | 本轮坐实的误读写法数 | 用来解释"这轮为什么人数对得上" |

上限 `ROSTER_HISTORY_MAX=24` 轮，超出从头部丢（存的是时间顺序，看的是倒序）。

### 视图（`churn_dialog`）

点【成员变动】：顶部一句话（最近一轮 / 采到几人 / 页面几人 / 累计几轮），中间轮次表
（最新在上，未采完整行压暗、移出标红），下面选中那轮的详情，再下面是"当前连续没见到"的人。

两条只提示、不动作的判据：

| 现象 | 工具怎么说 | 为什么不自动处理 |
|---|---|---|
| 上一轮恰好 1 进 1 出 | 「可能是改名，不是换人」 | 公会里改名远比"走一个又来一个"常见，但**真走了又来新人**时自动合并会把两个人的记录搅在一起 |
| 某轮 `ok=false` | 「没采完，人数和新增都不可信」 | 半轮采集中间断掉，少几个人太正常；连"新增"都可能是漏采导致的重认 |

### 纯函数抽出来是为了能单测

`roster_history()` / `churn_headline()` 都不碰界面。理由是**这条判据错了界面上看不出来**：
把没来的人写成退会，只会显示成"移出 1 人"，看着还挺正常。`churntest.py` 55 项里
有 30 项是围着这两个函数转的（未采完不记未见、连续两轮才移出、首轮不刷新增、上限裁剪、脏数据容错）。

### 顺手补的两个洞

1. **移出库不进摘要**：以前 `names.pop()` 之后只写一行 WARN 日志，收工那句
   "本轮 32 人 · 库内 32 人"看不出有人被移出过。移出是不可逆的（下次进来算新人），必须点名。
2. **`roottest` 的 Fake 少了 `_total_hint`**：落档要用它记页面人数。补上字段而不是在代码里
   写 `getattr(..., 0)`——真 App 一定有这个属性，`getattr` 只会把"忘了赋值"藏起来。
